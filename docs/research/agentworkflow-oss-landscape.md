# Open-source landscape for Agentworkflow

_Research snapshot: 2026-08-24. Sources are project-owned repositories, documentation, specifications, and releases._

## Conclusion

There is no mature open-source exact equivalent. The closest overall workflow experience is **Flow-Next**: durable specs, criterion-to-task traceability, fresh workers, cross-model plan and implementation reviews, and per-task receipts. **AI-SDLC**, **ASDD**, **Kaji**, and **BMAD + bmad-loop + TEA** cover substantial parts of the same lifecycle. None of them combines Agentworkflow's exact candidate identity, engine-executed direct checks with captured output and before/after hashes, independently reviewed immutable snapshots, integrity-checked evidence generations, and explicit source-drift-safe promotion in one fail-closed engine.

The market divides into three layers:

1. Spec/review methodologies: Flow-Next, BMAD, Spec Kit, OpenSpec, SpecD, agent-sdlc.
2. Workflow/governance runtimes: AI-SDLC, Kaji, ASDD, OSpec, bmad-loop.
3. Receipt/audit substrates: Weft, Agent Spec, and GitHub Agentic Workflows (`gh-aw`).

A practical reuse strategy would compose a mature spec/review layer with a receipt runtime. A wholesale replacement would currently give up material guarantees.

## What Agentworkflow means in this comparison

The **current implementation** is a guarded evidence-qualification engine, not a general workflow language. It reads the project-owned `.spec/agentworkflow.yaml`, but the recipe is deliberately fixed: each of `discover → plan → implement → check → review → repair → apply` appears exactly once and in order. Projects can enable stages and edit stage prompts, while the engine retains permissions, output schemas, loop bounds, evidence invalidation, and explicit-apply semantics. It copies the source into private base and candidate workspaces; validates a typed objective, numbered criteria, constraints, and a criterion-to-plan/verification mapping; optionally performs independent high-assurance plan review; runs declared checks itself; captures command, exit code, stdout/stderr, duration, and pre/post candidate hashes; rejects check mutation; sends immutable candidate copies and their digest to independent reviewers; validates finding locations; invalidates stale evidence after repair; and promotes only through a qualified apply operation with source-drift detection and rollback. Its store also verifies generation and artifact digests. See the local [overview](../../tools/agentworkflow/README.md), [request and workflow types](../../tools/agentworkflow/request.go), [workflow implementation](../../tools/agentworkflow/workflow.go), [result contract](../../tools/agentworkflow/result.go), [artifact store](../../tools/agentworkflow/internal/store/store.go), and [workspace boundary](../../tools/agentworkflow/internal/workspace/workspace.go).

The [YAML workflow design](../superpowers/specs/2026-08-23-agentworkflow-yaml-workflows-design.md) is now implemented in the current working tree. It is important not to compare its YAML syntax alone with a general DAG engine: Agentworkflow's control surface is intentionally a configurable guarded recipe, while Kaji and Spec Kit expose substantially more control flow.

## Capability taxonomy and enforcement legend

The comparison below separates an attractive workflow description from a guarantee the runtime can actually establish.

| Capability | Comparison question |
|---|---|
| Control surface | Is the lifecycle a guarded recipe, a general graph, or a set of independently invoked skills? |
| Intent/spec | Is the requested behavior durable and structurally validated before implementation? |
| Criteria traceability | Can each success criterion be followed into implementation work and verification evidence? |
| Isolation/candidate identity | Does mutation happen away from the source, and is the exact review/verification subject unambiguous? |
| Execution receipts | Does the runtime execute checks and retain the exact command, result, and useful raw output—not merely accept an agent's claim? |
| Quality/completion gate | What exact combination of checks, reviews, thresholds, and exceptions permits a successful terminal state? |
| Independent review | Is review separated from implementation by model, session, role, permissions, and/or immutable subject? |
| Repair/requalification | Are fixes bounded, and must all affected evidence be reproduced after mutation? |
| Integrity/provenance | Can stored evidence be detected as stale, substituted, edited, or detached from its subject and policy? |
| Promotion | Is moving qualified work into the source/merge target a distinct checked operation? |
| Resumability/recovery | Can a run continue without silently changing its admitted contract or replaying an ambiguous mutation? |
| Human gates | Where does a human explicitly own readiness, exceptions, application, or merge? |

Enforcement tags used in the matrix:

- **E — engine-enforced:** executable runtime behavior fails or stops when the invariant is not met.
- **A — artifact/protocol-enforced:** a schema, CLI, CI rule, or normative protocol can validate the invariant, but it is not necessarily the mutation runtime's invariant.
- **P — prompt/process:** an agent skill, methodology, or documented convention asks for the behavior.
- **O — optional:** available only through configuration, an add-on, a separate mode, or an experimental runtime.
- **—:** no first-party mechanism was found. Absence means “not documented in the reviewed primary sources,” not proof that no integration can be built.

## Strongest matches

### Flow-Next: closest overall

Flow-Next explicitly treats the spec as the unit of work. Capture source-tags acceptance criteria, planning maps stable R-IDs to dependency-ordered tasks, workers re-read spec/task/git state in fresh contexts, and a different model can review both plan and implementation until a `SHIP` verdict. Receipts feed an R-ID→task→evidence-commit table in the PR. Its external Ralph loop adds fresh-session retries and on-disk receipts. These are the closest semantics to Agentworkflow's spec traceability and independent review model in one usable project. The important trust-boundary gap is that `flowctl` records commits, tests, evidence, and review verdicts inside the working repository; its documentation does not claim that receipts contain raw exact check outputs bound to immutable before/after candidate hashes, or that reviewers only see an integrity-verified frozen candidate. [Official README](https://github.com/gmickel/flow-next#what-you-get), [Ralph documentation](https://github.com/gmickel/flow-next/blob/main/plugins/flow-next/docs/ralph.md).

### AI-SDLC and ASDD: closest governance models

AI-SDLC defines versioned resource schemas for pipeline steps, decisions, roles, quality gates, autonomy policy, and adapters. Its experimental autonomous runner admits work, creates isolated worktrees, runs a developer and three reviewers, signs DSSE attestations, quarantines failures, and opens a PR for human merge. The [pipeline CLI](https://github.com/ai-sdlc-framework/ai-sdlc/blob/main/pipeline-cli/README.md) also documents an instructive failure: manually skipped steps allowed PRs without reviewer verdicts, motivating a composite `execute` path. Cross-harness verification is a meaningful independence control, but v1alpha1/experimental status and less complete check/candidate receipt semantics keep it below Agentworkflow's assurance boundary.

ASDD separates specification, external implementation, deterministic intake, read-only multi-lens review, and write-scoped publication. Its [spec-driven profile](https://github.com/OneHillAI/ASDD/blob/main/standards/spec-driven.md) is unusually explicit about claims and reviewer roles; the optional [Assure profile](https://github.com/OneHillAI/ASDD/blob/main/standards/assure.md) binds identity, provenance, threat scan, and independent-model review. It is a governance membrane around another build agent, not an isolated implementation/check/repair engine, and both the project and Assure profile are early.

### Kaji: closest general YAML review loop

Kaji defines resumable YAML state machines over design→implement→review→fix→verify→PR. It can route roles to different CLIs, executes deterministic subprocess steps directly, interprets structured `PASS`/`RETRY`/`BACK`/`ABORT` verdict artifacts, retains each attempt, and supports human gates. It is a useful contrast to Agentworkflow's implemented YAML: Kaji exposes a general transition graph, while Agentworkflow restricts configuration to the seven-stage guarded recipe. Kaji's control unit is the agent's verdict artifact rather than an immutable candidate plus independently reproduced evidence. [Official repository and workflow diagram](https://github.com/apokamo/kaji).

### BMAD + bmad-loop + TEA: strongest mature methodology and QA suite

BMAD supplies the deepest planning methodology and the largest adoption signal. bmad-loop turns planned stories into a deterministic fresh-session implement→verify→review→fix loop; verification reruns after review and worktree isolation is available. TEA supplies measurable quality artifacts: test quality scoring, NFR evidence audit, requirement→test coverage, and deterministic `PASS`/`CONCERNS`/`FAIL`/`WAIVED` release decisions. Its [command reference](https://github.com/bmad-code-org/bmad-method-test-architecture-enterprise/blob/main/docs/reference/commands.md) is especially strong on evidence thresholds, while [bmad-loop setup](https://github.com/bmad-code-org/bmad-loop/blob/main/docs/setup-guide.md) describes fresh coding sessions and layered reviewers. The remaining gap is architectural: the methodology, loop, and test architect are separate prompt/CLI layers, and do not jointly maintain Agentworkflow's immutable evidence/candidate/apply chain. BMAD's code is [MIT licensed with a trademark notice](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/LICENSE).

## Strong spec foundations, weaker qualification

- **Spec Kit** now has a real YAML [workflow engine](https://github.com/github/spec-kit/blob/main/src/specify_cli/workflows/engine.py): sequential steps, branches, bounded loops, fan-out/fan-in, persisted resume, prompt/shell/command steps, and human gates. It is not a security sandbox—the engine source deliberately treats workflow `requires` as advisory and rejects `permissions` so they cannot be mistaken for enforced controls. Core `analyze`, checklist, and convergence improve traceability, while MAQA adds coordinator/feature/QA separation. However, MAQA is a small community extension and Spec Kit's [community catalog](https://github.github.com/spec-kit/community/extensions.html) is format-checked rather than an endorsement/security audit. Neither core nor MAQA supplies exact candidate-bound receipt integrity.
- **OpenSpec** has excellent proposal/delta/design/task history and transactional archive behavior, but its [overview](https://github.com/Fission-AI/OpenSpec/blob/main/docs/overview.md) explicitly frames artifacts as enablers rather than gates. It is a good upstream spec format, not a qualification engine.
- **SpecD** adds schemas, symbol provenance, append-only history, approval actor/reason/hash fields, and approval invalidation. Yet its [workflow contract](https://github.com/specd-sdd/SpecD/blob/main/docs/guide/workflow.md) says nothing technically prevents `verifying → done`; readiness remains a judgment. Default approvals are optional and there is no candidate/check receipt chain.
- **agent-sdlc** has unusually good explicit traceability and a never-skip gate/TDD/checker philosophy, but it is a new skill/plugin framework and does not document immutable candidate generations or hash-bound raw outputs. [Official repository](https://github.com/smarzban/agent-sdlc).
- **OSpec** has a rich task/reviewer artifact model, review packages scoped to git diffs, bounded repair, and executor provenance. Its [usage contract](https://github.com/clawplays/ospec/blob/main/docs/usage.md) has the operator run a check and then pass the command, result, and exit code to `ospec execute verify`; the framework records rather than independently executes that proof.

## Useful complementary audit runtimes

- **Weft** is the strongest cryptographic substrate found. Its [protocol](https://github.com/spranab/weft/blob/main/rfcs/0001-weft-protocol.md) defines signed, content-addressed intents, policies, gates, evidence, manifests, capabilities, and certificates. It could strengthen Agentworkflow's receipts, but it is a tiny pre-1.0 version-control protocol without planning or review-repair orchestration.
- **Agent Spec** provides human-reviewable source excerpts, task contracts, criterion-specific test selectors, fingerprints, trace/replay, and risk-dependent evidence requirements. Its own [scope statement](https://github.com/ZhangHanDong/agent-spec#what-agent-spec-doesnt-solve) leaves architectural judgment, approval identity, and workflow enforcement external.
- **GitHub Agentic Workflows (`gh-aw`)** is a good CI-side complement. Agent jobs are read-only/sandboxed by default and safe outputs are buffered, validated, and applied in separately scoped jobs; [`gh aw audit`](https://github.github.com/gh-aw/reference/audit/) collects run logs/artifacts and compares activity across runs. It improves operational provenance but does not establish a spec, immutable local candidate, or a qualification certificate by itself.

## Recommendation

For ideas and adoption patterns, study **Flow-Next** first, then **AI-SDLC**, **Kaji**, and **BMAD/bmad-loop/TEA**. For a configurable workflow surface, Spec Kit's engine is the most mature reference but is deliberately more general and less capability-safe than Agentworkflow's implemented guarded YAML recipe. For receipt evolution, borrow from **Weft** (signed content-addressing), **Agent Spec** (criterion-specific verification and replay), and **gh-aw** (post-run audit).

Agentworkflow's defensible differentiator is not “spec-driven agents” alone. It is the conjunction of:

- typed, criterion-traceable intent;
- exact engine-run check outputs plus mutation detection;
- immutable candidate identity presented to independent reviewers;
- evidence invalidation after every mutation;
- integrity-verifiable generations and provider records; and
- explicit, drift-safe promotion from private candidate to source.

No reviewed project currently demonstrates that complete conjunction.
