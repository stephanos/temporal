# Restricted CEL for runtime predicates: adoption investigation

**Accepted direction: adopt CEL's standard AST and native CEL evaluation for runtime predicates.** Reusing a maintained expression language, its protobuf representation and its tooling is the architectural reason for adoption; deleting whole files is not a prerequisite. The current Testpilot/Umpire language is not automatically the right specification. Prefer standard CEL semantics where differences are incidental, while retaining domain rules that make Cases meaningful and admissible. The user accepted this direction following the prototype investigation. Implementation and migration remain outstanding; the prototypes do not establish that every supported Case already translates.

The investigation compares local consumers and tests with CEL's primary sources and an isolated executable probe. No production schema, dependency or behavior changed. Finite model `Expr`, tables, refinement and model checking remain outside this scope. Testpilot cannot import Umpire, and realization admission cannot depend on Testpilot; both can depend on CEL's neutral schema without importing each other. A shared domain adapter, if needed, would require a documented leaf-module boundary. [Module map](UMPIRE_MODULES.md#module-ownership), [Spec](UMPIRE4_SPEC.md#source-of-truth), [architecture](UMPIRE4_VISION.md#high-level-architecture).

**There are three existing predicate domains, not one interchangeable evaluator.**

1. Testpilot's general expressions serve Program inputs/guards, Contract predicates/captures and evidence lifts. They bind descriptor-specific types and availability facts before evaluation.
2. Correlated conditions use the same wire `Expression` but separate admission and evaluation; step references have existential, potentially multivalued meaning.
3. Umpire's offline evidence guards evaluate `Operand` over an instruction outcome. Crucially, comparing absent values is an **error**, whereas a Testpilot comparison with an absent operand is **false**. Both behaviors are documented and tested; that establishes migration impact, not that both are desirable. Decide explicitly whether strict missing-value errors should become the shared rule. [expression.go](../common/testing/testpilot/internal/ir/expression.go#L55), [correlated.go](../common/testing/testpilot/internal/verification/correlated.go#L309), [guard.go](../tools/umpire/conformance/guard.go#L125), [SEMANTICS](../model/SEMANTICS.md#L596).

**Current behavior and migration impact**

The last column describes the work needed for exact compatibility, not requirements to retain every behavior. The adoption proposal below deliberately changes several of them.

| Concern | Current requirement | Consequence for a replacement |
|---|---|---|
| Absent / null / default | Absence is a nil resolved value, not a literal. `Value` has no null arm. Present ordinary proto3 scalars yield their default even when never explicitly set; unset messages/optional fields/oneof members and missing map keys are absent. `present(default scalar)` is true. | Use explicit presence alongside typed values; do not encode absence as null or conflate it with protobuf default values. |
| Equality and absence | Every Testpilot comparison, including `!=`, is false if either side is absent. Consequently `not(x == y)` differs from `x != y` when absent. Offline Umpire guard comparisons instead error. | Preserve site-specific absent policies; standard comparison substitution alone is insufficient. |
| Boolean order | Testpilot All/Any evaluate left to right and stop at the first decisive operand; an earlier error is returned immediately. All with no operands is true and Any is false. Umpire and correlated admission reject empty groups. | Preserve operand order, errors, and domain-specific admission even if a Boolean algebra rewrite seems equivalent. |
| Integers | Canonical decimal strings encode signed/unsigned values exactly. Expected protobuf scalar kinds remain distinct (`int32`, `sint32`, etc.); comparisons require identical declared types, with numeric-only ordering. | Retain descriptor type checks and bounds; no floating-point intermediary or widening that admits formerly invalid inputs. |
| Floating point | Float32 operands are rounded before comparison; float and double equality consider NaN equal to NaN; all ordered NaN comparisons are false; signed zeros compare equal. | Probe these explicitly; generic numeric equality cannot be presumed equivalent. |
| Enums | Literal names require contextual enum descriptors; two enum literals alone cannot infer a type. Runtime extraction uses the first declared name for a number, or decimal spelling for an unknown number. Equality compares stored spelling, so aliases need care. Offline guards reject unknown enum numbers. | Keep enum identity, literal admission and spelling behavior; an integer-only representation loses information. |
| Collections / protobuf equality | Lists compare in order, maps independently of entry order, typed messages by decoded `proto.Equal`. Whole `AnyType` values compare their envelopes as `Value` data and expose no payload traversal. | Typed-message and opaque-Any equality must remain distinct; preserve map/list behavior and recursive float handling. |
| Paths | Field, repeated wildcard, typed map key, final presence selector and named oneof member are supported. Wildcards preserve order, flatten traversal and enforce per-step fanout; nested collection output is rejected. If any projected leaf is absent the entire projection is absent; an empty projection is present. | Existing path machinery remains useful even if predicates change; collection macros are not automatically the same projection. |
| Presence selector | A final `?` is admitted only for presence-bearing fields. It returns false through absent parents; wildcard presence yields a Boolean per element. | Distinguish `present(path)` from a presence-valued path and from mere scalar non-defaultness. |
| Resources | Binding checks structure/work/depth; evaluation charges nodes, encoded values, traversal, fanout, comparisons and—in execution—ownership copies. Cancellation is checked. Exact budget and one-below-budget tests exist. | Engine operation counts cannot silently replace current accounting; charge adapter work and retain limits or define an explicit versioned migration. |

**Domain admission and dataflow remain substantial responsibilities.** Program references are limited to scoped Slots, ancestor instruction outcomes and permitted run/environment uses; Contracts see declared Observations, event fields/payload arms, captures and instance values. Evidence lifts read only their projected value. Opaque handles cannot be inspected, even for presence. Environment substitution is permitted only for whole request assignments. Availability is proved from exact reference/path presence facts, including AND/OR intersection rules, preceding branch conditions and successful dependencies. `successFacts` recognizes outcome-status equality and promotes only appropriate ancestor results and nonoptional Slots. Instance values must retain the admission and runtime work of their literal expansions. A general expression checker does not establish these graph facts. [expression.go](../common/testing/testpilot/internal/ir/expression.go#L190), [dataflow.go](../common/testing/testpilot/internal/execution/dataflow.go#L630), [prepare.go](../common/testing/testpilot/internal/verification/prepare.go#L436).

Correlated FACT equality means **any matching fact**, and STATE checks the atom plus structured state fields. Captures are identified by operation and exact zero-based occurrence; a future/unretained occurrence is absent, never the nearest match. Trigger/response reference classes, capture lifetimes, retained/redacted fields, step graph order and atomic monitor admission remain outside a pure evaluator. Only text, canonical uint64 and Boolean retained values are comparable. [correlated.go](../common/testing/testpilot/internal/verification/correlated.go#L309), [correlated_prepare.go](../common/testing/testpilot/internal/verification/correlated_prepare.go#L48), [capture tests](../common/testing/testpilot/internal/verification/correlated_captures_test.go#L123).

Umpire adds symbolic fixture-name substitution, learned-value declarations and source positions. Offline guards admit payload-only scalar comparisons and plain-field/oneof paths; they forbid fixture names, collection comparisons and message equality. Lowering preserves each operand's source position when available; Testpilot diagnostics identify Case sites, nested operand indexes and invalid reference arms. Any AST translation needs a stable node-to-Scala-position/Case-path map and deterministic first-error behavior. [operand.go](../tools/umpire/realization/operand.go#L52), [payload.go](../tools/umpire/realization/payload.go#L83), [lowering](../tools/umpire/lower/realization.go#L884), [reference diagnostics](../common/testing/testpilot/internal/ir/expression_test.go#L484).

**Which semantics should change?**

- **Missing comparisons:** prefer CEL errors on unguarded missing inputs and explicit presence guards. Testpilot currently makes both `missing == x` and `missing != x` false, yet the `ComparisonOperator` comment promises negation. The test explicitly records the exception. This is surprising language design, not a functionality worth preserving by default. Offline guards already use strict errors. Define error-to-verdict handling explicitly: an evaluation error must not silently become a successful assertion or an ordinary false guard. [proto comment](../proto/internal/temporal/server/api/testpilot/v1/expression.proto#L58), [absence test](../common/testing/testpilot/internal/ir/evaluate_test.go#L77).
- **Boolean error behavior:** prefer CEL's standard `&&`/`||` behavior, where a decisive false/true can suppress another operand's error. Domain validation must still reject forbidden references anywhere in the AST, including branches evaluation never reaches. If a particular site truly requires ordered error propagation, nested conditionals can implement it; do not impose this compatibility layer everywhere without a use case.
- **NaN and enum aliases:** favor ordinary CEL numeric equality, including NaN unequal to itself and protobuf enum aliases comparing by number. Preserve enum descriptor identity and valid request-field assignment at the boundary where needed. These changes remove spelling-sensitive equality and protobuf-value-container quirks from predicate meaning. Unknown enum-number policy needs an explicit decision, particularly for offline conformance.
- **Numeric precision and field assignment:** retain exact int64/uint64 values and range/type checks when writing protobuf fields. CEL's broader numeric comparison rules can replace the current requirement that comparison operands have identical protobuf scalar kinds. A protobuf float32 must still enter CEL as its actual rounded value: normalization of the input is necessary even when adopting CEL semantics.
- **Presence:** use ordinary CEL protobuf presence for exposed messages. Do not call it equivalent to current `Present`: an implicit scalar default is readable but generally does not satisfy CEL `has`. Migrate existing availability checks according to their intent. A supplied binding containing zero must remain distinguishable from an unavailable binding.
- **Paths and correlation:** retain capabilities such as typed map access, wildcard projection, opaque handles and exact capture ordinals. Their current encodings need not survive. Existential matching over correlated facts should become an explicit domain operation or collection predicate, rather than silently overloading scalar equality. Whether mixed-absence wildcard projection should fail or filter is a separate domain decision; do not accidentally change it while replacing Boolean operators.
- **Budgets:** retain bounded preparation, evaluation, traversal, fanout and memory ownership. Exact historical work totals are not intrinsically valuable. Adopt a documented CEL cost budget plus separately charged adapter work, and regenerate budget expectations under a versioned policy.

The CEL Boolean rules are specified in its [language definition](https://github.com/google/cel-spec/blob/master/doc/langdef.md). Numeric equality implementation is visible in [double.go](https://github.com/cel-expr/cel-go/blob/v0.32.0/common/types/double.go); engine cost options are in [options.go](https://github.com/cel-expr/cel-go/blob/v0.32.0/cel/options.go). These are proposed semantic changes to review against actual authoring intent, not compatibility claims.

**A concrete restricted representation**

Use `cel.expr.Expr` as the shared expression AST, with source metadata alongside it. CEL already models constants, identifiers, selection and function application; operator-specific messages are unnecessary. Node IDs provide an anchor for diagnostics. `CheckedExpr` adds type/reference maps, but supplied checker output is not proof that our admission rules passed. Prefer an unchecked canonical AST in artifacts and check it during preparation; cache checked programs locally against the pinned environment. [syntax.proto](https://github.com/google/cel-spec/blob/master/proto/cel/expr/syntax.proto), [checked.proto](https://github.com/google/cel-spec/blob/master/proto/cel/expr/checked.proto).

A small owning wrapper would carry the CEL AST, a language/environment revision, typed binding declarations and source attribution. CEL identifiers refer to declared bindings. Existing domain reference messages, or a neutral equivalent, describe where each binding comes from; they are not encoded as arbitrary strings containing executable paths. Umpire resolves symbolic fixture and role references during lowering and emits the executable binding declarations. This shares expression syntax without making a symbolic Realization an executable Case.

Start with Boolean/scalar literals, declared identifiers, approved field/map selection, comparison, negation, conjunction, disjunction and conditional expressions. Admit complex-value equality through well-defined bindings so the restriction does not simply discard supported message/list/map cases. Disallow arbitrary functions, dynamic type escape hatches, message construction and unrestricted comprehensions initially. Check every node, operator, arity and inferred type; a Boolean predicate site must produce Boolean. Disable unapproved parser macros and also validate serialized ASTs, because callers can bypass parsing. CEL's [custom environments](https://github.com/cel-expr/cel-go/blob/v0.32.0/cel/env.go) and [standard-library subsets](https://github.com/cel-expr/cel-go/blob/v0.32.0/cel/library.go) support restricting the available language, but do not replace our domain admission.

Supply bindings lazily, or explicitly preserve missing/error states until selected, so an irrelevant missing input does not fail preparation of every predicate. Keep descriptor-aware paths behind the binding boundary initially. Use CEL operators for ordinary predicate meaning; add only necessary domain operations for availability/projection/correlation. Resolve capture scope, ancestor constraints, payload arms, opacity and availability proofs before execution. CEL type checking cannot replace these checks. Existing dataflow recognizers must learn the admitted CEL AST patterns, including success-status comparisons and presence guards.

Testpilot `Expression` also carries request inputs and captured values. Replacing only Boolean sites introduces a temporary second representation; therefore inventory all call sites and plan an eventual shared CEL AST for supported value expressions as well. Keep protobuf request construction, symbolic templates and runtime ownership outside that AST. Do not replace every `Value`, `ValueType` or `ProtoValue` with CEL types merely because the expression schema changes.

Dependency details matter: this checkout already indirectly uses `cel.dev/expr v0.25.2`, but has no CEL evaluator dependency. The current implementation is `cel.dev/cel-go` from `cel-expr/cel-go`; the old Google repository points to the new home. The experiment used v0.32.0. Importing CEL protos also requires making the canonical proto sources available to Go generation and ScalaPB; the existing Go module alone does not establish that toolchain integration. Use one CEL proto package consistently, rather than mixing `cel.expr` and the older `google.api.expr.v1alpha1` types. [go.mod](../go.mod#L100), [CEL repository](https://github.com/cel-expr/cel-go), [migration notice](https://github.com/google/cel-go), [model generation](../model/check/Gate.scala#L168).

**Executable comparison**

An isolated temporary Go module imported the current Testpilot internal evaluator through a local module replacement and CEL v0.32.0 with `cel.dev/expr v0.25.2`. All 15 table cases passed using `go test -mod=mod -tags test_dep -v .`; passing means the asserted differences/adaptations were observed, not that the languages are equivalent.

| Probe | Current Testpilot | CEL without compatibility adapters |
|---|---|---|
| Missing equality, inequality, both operands missing | false | error |
| NaN equality / inequality | true / false | false / true |
| NaN ordering | false | false |
| Values equal after float32 rounding | true | false if incorrectly supplied as unrounded doubles |
| `9007199254740992 < 9007199254740993` | true | true with CEL int values |
| Missing `p` in `p && false` / `p || true` | current evaluator propagates the earlier absence | CEL false / true |
| Missing `p` in `p ? false : false` / `p ? true : true` | not a current AST form | CEL error |
| `false ? p : false` | not a current AST form | CEL false without evaluating `p` |
| `present_a ? a == b : false`, and inequality variant | legacy absent result is false | CEL false when `present_a` is false |

The Boolean rows exercised CEL directly; current Testpilot order is supported by source/tests. Runtime comparison costs were 3–39 work units in these probes versus CEL costs of 1–3, demonstrating incompatible accounting units. Enum aliases, Any behavior, full corpus translation and Scala generation were not experimentally validated. The temporary harness is not a checked-in conformance suite; these results justify a prototype, not rollout.

**Reuse and deletion potential by design**

Schema reuse is valuable independently of immediate deletion: it gives both producers one established AST and a route to shared checking, diagnostics and evaluation. Schema-only adoption can be a migration stage. As a permanent endpoint, however, a bespoke interpreter over CEL nodes should be described as a custom dialect, not assumed interoperable CEL.

| Design | What could disappear | What remains or replaces it |
|---|---|---|
| CEL schema only; current evaluator | Some wire declarations and AST-specific switches after rewriting them against CEL nodes. No evaluator file disappears. | Restricted-node validation, typed references, paths, evaluation and all compatibility rules. Migration and source maps add code. |
| Restricted CEL engine plus full adapter | The generic portions of `compiler.node`, `unary`, `binary`, `logicalNode`, `pair`; `runtimeExpression.eval` Boolean dispatch and conventional scalar ordering; potentially offline `evaluate` composition and correlated `correlationHolds` composition. | Custom type/presence/refinement checks, nonstandard equality/absence, cost accounting, references, snapshots, paths, symbolic lowering and error translation. Removing a file by moving these functions into adapters is not a net deletion. |
| Narrow pure-predicate kernel with typed bindings | Boolean/comparison dispatch could be shared across the three domains; `realization.TypeOf`'s generic Boolean checks might delegate once input types are known. | Existing bindings supply values/presence and policies; ordered evaluation must stay lazy. A scalar-only kernel preserves supported complex equality through fallback or custom operators, reducing its deletion benefit. |

Concrete bounds: `ir/expression.go` is 725 lines; `evaluate.go` 267; `evaluate_path.go` 272; `runtime_value.go` 96. **None is demonstrated wholly deletable.** `expression.go` mixes generic checking with reference admission, immutable binding, presence proof and literal-expansion accounting. `evaluate.go` also owns the budget machinery that path reads reuse. `evaluate_path.go` serves `ReadValue` independently of expressions; `decodeMessage` also serves request writing. All 96 snapshot lines remain because values still cross Driver/Run ownership boundaries. [read.go](../common/testing/testpilot/internal/ir/read.go#L137), [write.go](../common/testing/testpilot/internal/ir/write.go#L52), [runtime_value.go](../common/testing/testpilot/internal/ir/runtime_value.go#L30).

`conformance/guard.go` is 185 lines: `evaluate`, `needed`, `sides` and `valueAt` occupy roughly its last 100 lines; deleting them requires replacing both strict absence and descriptor projection. `realization/operand.go` is 163 lines and `payload.go` 157: their policies still need representation. `lower/realization.go`'s final ~130 lines implement literal conversion, reference restrictions and operand translation; shared syntax removes some recursive copying, but symbolic substitution, source attribution and restrictions remain. Correlated `predicate`, `operandValue`, `correlationHolds` occupy ~100 lines, mostly domain semantics; `validOperand`/`validCorrelation` likewise retain policy. These are inspection bounds, **not additive savings estimates**. No production-file deletion is justified by schema adoption alone.

**An actual integration issue was found and exercised.** CEL-Go v0.32.0's `cel.ParsedExprToAst` accepts `google.api.expr.v1alpha1.ParsedExpr`, not the canonical `cel.expr.ParsedExpr`. Directly passing canonical Go structs fails compilation. The prototypes serialize the canonical message and decode into the legacy API type at the engine boundary. Both directions round-trip for the tested AST and checked metadata. Keep the stored schema canonical and isolate this bridge; reject unsupported extensions and unknown fields before conversion. This narrows the earlier advice to avoid mixing packages: one canonical artifact format is still appropriate, but this engine currently needs an explicit boundary conversion. [CEL-Go AST loader](https://github.com/cel-expr/cel-go/blob/v0.32.0/cel/io.go#L74).

The Scala probe built `phase == 2 && attempt < 3` directly as an AST. Its invalid variant produced `model/Probe.scala:1:24` in Go's checker diagnostic. Scala read seven checked types and five references back from Go. Generation emitted deprecation/JDK warnings but succeeded with the repository's pinned ScalaPB 0.11.20 and Scala 3.9.0 configuration.

**Limits of the corpus result.** This is an expression-kernel simulation, not live execution or RecordedRun replay. Complete reference/path leaves are replaced by synthetic typed bindings in both sides of the comparison. Types are inferred from scalar literals and known reference forms; presence-only leaves can use Boolean placeholders because their values are never inspected. The prototype does not prove authoritative descriptor/path binding or narrower protobuf integer-width checks; signed integer literals use int64. Correlated fact references are treated as scalar inputs, so existential matching, capture lifetimes and exact occurrence selection remain untested. It also does not test Umpire symbolic lowering, instruction dataflow proofs, wildcard projections or preservation of ownership. Those remain real work even though all 358 roots compile.

The compatibility variant inserts explicit presence guards and conditional Boolean composition. Zero differences in that variant is evidence that selected old semantics can be retained where justified, not a recommendation to preserve them globally. The native variant still uses explicit availability bindings for existing `present` nodes; it is not a conversion of those nodes to CEL `has`. Its differences should drive an intentional semantic decision and migration tests. The small corpus does not exercise every supported operator/type; separate probes cover additional numeric, list/map and admission behavior.

**Remaining migration decisions.** Adoption is settled; the following details determine the implementation contract and rollout evidence:

| Area | Direction and closure evidence |
|---|---|
| Missing inputs and verdicts | Use CEL missing-input errors and explicit guards where absence is expected. Define how errors become evaluation failures or inconclusive results at each site; verify online/offline agreement. |
| Presence and projection | Distinguish value availability from protobuf `has`. Specify nested optional fields, map misses and mixed-absence wildcard projection with real descriptor-backed examples. |
| Numbers and enums | Use CEL comparisons; normalize float32 inputs and retain exact integers and assignment bounds. Decide unknown-enum admission and nominal enum-domain checks at the binding boundary. |
| Correlated facts and captures | Preserve existential fact matching, capture scope and exact occurrence selection through explicit bindings or domain operations. Exercise multiple facts and missing capture ordinals. |
| Resource limits | Define CEL cost plus bounded adapter traversal, allocation and cancellation. Test exhaustion and its verdict instead of preserving historical work-unit totals. |
| Artifact migration | Pin the language environment and define conversion/versioned reading, deterministic identities and historical Case/Run pairing. Reject unsupported AST features before the engine bridge. |

Resolve these against domain intent and executable examples. Update the specification before relying on changed semantics, and update the Model independently of implementation. The completion criterion is explained semantic differences, preserved supported capabilities and agreement on real event data across online and offline evaluation—not exact reproduction of every old evaluator quirk.

**Recommended changes, in order**

1. **Implement the accepted CEL direction.** Reuse `cel.expr.Expr` and native CEL checking/evaluation in a versioned restricted environment. Use standard CEL operator semantics by default; require a concrete domain requirement for exceptions. Keep finite model `Expr` separate. Domain integration checks gate rollout, rather than reopening whether to adopt CEL.
2. **Record intentional semantic changes.** Prefer standard missing-value errors, Boolean error handling, NaN equality and enum-number equality. Review presence, unknown enums, error verdicts, correlated facts and wildcard behavior by use case. Update the specification and Model independently of implementation; a conformance failure still requires human judgment rather than fitting the Model to the code.
3. **Extend the proven kernel into one complete domain path.** Scala/Go generation, source diagnostics, AST restrictions and corpus syntax now have executable evidence. Next connect a real symbolic predicate to authoritative typed bindings, lower it into a Case, execute it against actual event data and replay the same data offline. Include a correlated fact/capture case and a wildcard/presence case. Compare retained adapter complexity; do not count the synthetic corpus probe as completion of this step.
4. **Translate and evaluate the corpus with categorized differences.** Separate intended semantic changes from regressions. Add targeted cases for missing/default values, NaN, float32, large integers, enum aliases, Any/message equality, wildcard absence and repeated facts/capture ordinals. Ensure all supported capabilities have an encoding or an explicit decision; current generated-case frequency alone is not a deletion criterion.
5. **Version the environment and migrate artifacts deliberately.** Pin functions, types and cost policy; define deterministic AST IDs and metadata hashing. Regenerate Cases and their identities, preserve historical Case/Run pairing, and choose conversion or versioned reading for old artifacts. Do not silently re-evaluate old Cases with new semantics.
6. **Remove duplicate expression machinery after the migration.** Replace generic recursive syntax, type-checking and evaluation where CEL owns it; retain domain admission, projection, ownership and correlation logic. Measure both maintenance simplification and ecosystem reuse, not just whole-file deletion. Avoid a permanent pair of almost-identical predicate languages.
