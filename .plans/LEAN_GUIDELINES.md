# Lean Authoring Guidelines

Read this before creating, changing, or reviewing Lean 4 code in this repository. The target is
idiomatic Lean that a reader still learning Lean can follow: standard notation, proof techniques,
and abstractions, explained at module and API boundaries rather than line by line.

Authoring runs through six steps, each ending on a completion criterion: orient, design, prove,
document, bound trust, verify. A read-only review applies steps 2 through 5 as evaluation criteria,
runs only the non-mutating checks from step 6, and reports the authoring checks the implementation
still owes.

## 1. Orient

The workspace is the source of truth. Mirror its naming, namespaces, imports, formatting, and proof
style wherever they differ from the general guidance below.

1. **Find the owning workspace.** Each Lake workspace pins its own `lean-toolchain` and dependency
   set, and the workspaces in this repository pin different ones. Locate every workspace that
   compiles or imports the changed source:

   ```sh
   find . -name lean-toolchain -not -path '*/.lake/*'
   ```

   `model/` is the primary workspace; its build, regression, and lint entry points are in
   [model/README.md](../model/README.md) under "Build and regression". Run Lake the way the
   `Makefile` does (`mise exec -- lake`, with the SDK and compiler variables it exports), so the
   pinned toolchain and native compiler are the ones used.
2. **Classify each file as authored or generated.** A generated module opens with
   `-- Code generated by <owner>. DO NOT EDIT.`. For a generated change, edit the owner or its
   input, regenerate the complete owned surface with the owner's `make` target, and run the owner's
   check target. [model/README.md](../model/README.md) names the owners.
3. **Learn the local style.** Read the imports and neighbouring modules, and identify the intended
   public API from the documented facades and module boundaries. Workspaces here follow Lean Std
   or Batteries conventions; `tools/umpire3/model` also depends on mathlib.
4. **Search before adding.** Look through the workspace and its `.lake/packages` for an existing
   definition, theorem, instance, or notation that covers the requested behaviour. Keep the
   toolchain and import set fixed: a proof that wants a broader import or a new dependency is a
   signal for a missing local lemma, not a reason to widen the workspace.

Orientation is complete when the owning workspace, each target file's ownership, the reusable API,
and the verification commands are known.

## 2. Design declarations as interfaces

A theorem statement or definition signature is an API. Prefer the clear, reusable statement over
the one whose first proof is shortest.

*Public* means part of an intentional exported API identified by the project's facades and
documentation, not every declaration that lacks `private`.

- Give public arguments and return values explicit types.
- Put operations and theorems in the namespace of their principal type, so names are predictable
  and dot notation works.
- Name per the local convention. Under Lean Std and mathlib conventions: `UpperCamelCase` for
  types and propositions, `lowerCamelCase` for functions and values, `snake_case` for theorems.
- Put ordinary inputs and hypotheses left of the colon:

  ```lean
  theorem result (x : α) (h : P x) : Q x := by
    ...
  ```

- Use the short conventional names `α`, `x`, `h` in small generic scopes, and domain names when a
  value has a stable role or a proof is long enough for short names to blur.
- State theorems in the library's established normal forms.
- Introduce notation, coercions, instances, or attributes only as part of a coherent reusable API.
- Mark a theorem `@[simp]` only when it reliably rewrites toward the agreed canonical form and its
  right-hand side is simpler than its left.

### Deep modules

Encapsulate a complicated representation behind a small semantic API: the constructors, accessors,
elimination principles, extensionality lemmas, and simplification lemmas callers need.
Representation-specific lemmas stay private or clearly separated from the public interface.

Downstream proofs use API lemmas rather than the representation. Repeated `unfold`, `erw`, a
representation-specific `change`, or a cleanup `rfl` after an API operation are signals of a
missing lemma; add the lemma rather than the workaround.

Design is complete when callers can use the declaration through stable semantic names without
knowing its representation.

## 3. Write legible proofs

Expose the main argument; let automation close routine leaves.

- A direct proof term for genuinely simple proofs.
- `calc` for equality, inequality, and other transitive chains.
- Tactic mode for multi-step proofs, one conceptual step per line.
- `have`, `suffices`, or `show` to name important intermediate statements, with an explicit type on
  any nontrivial one.
- Bullets or named `case` blocks whenever a tactic opens several goals.
- Semantic library lemmas over unfolding or incidental definitional equality.
- `simpa using ...` when only routine normalisation remains.
- Domain automation (`simp`, `omega`, `decide`, and, where imported, `ring`, `linarith`,
  `norm_num`, `aesop`) when it communicates the method more clearly than its expansion. Confirm the
  narrow import that provides a tactic before relying on it.
- Search commands and tactics (`#check`, `#print`, `exact?`, `apply?`, `simp?`, `aesop?`) during
  exploration; the finished proof carries their stable result or an intentional terminal call.
- In `simp`, name the definitions or nonstandard lemmas that explain the important reduction. A
  clear terminal `simp` beats a generated wall of default `simp only` lemmas.
- Expand long semicolon chains, broad `<;>` expressions, and deeply nested anonymous terms when
  they hide which goal is being solved.

Prefer visible structural reasoning when the structure is the point:

```lean
example (P Q : Prop) (h : P ∧ Q) : Q ∧ P := by
  obtain ⟨hP, hQ⟩ := h
  exact ⟨hQ, hP⟩
```

A proof is complete when its structure says why the result holds, its automation is intentional,
and Lean accepts it without placeholders.

## 4. Document the boundary

Documentation bridges Lean syntax and the project's domain at boundaries, without translating each
line.

**Module docstring.** A new substantial module, or one whose purpose or API boundary materially
changes, opens with a `/-! ... -/` block covering the problem it addresses, its central types, its
main invariants or chosen normal form, its important entry points, and any non-obvious notation or
design decision.

**Declaration docstrings.** New or materially changed public definitions and major theorems get a
`/-- ... -/` docstring that reads on its own in an editor hover: a theorem's meaning in plain
English; a definition's concept, edge cases, and observable behaviour. Add a small checked example
when it is the clearest documentation or regression for an important user-facing API.

**Comments.** Preserve existing comments when changing or refactoring code, and update any comment
whose invariant or behaviour changed. A comment explains intent, an invariant, a proof phase, or a
non-obvious representation change, sits next to the code it explains, and says why the step exists
rather than paraphrasing its syntax.

Documentation is complete when a reader can identify the module's purpose and the meaning of each
new or materially changed public declaration before reading its implementation. Document the
declarations the change touches; leave unrelated declarations as they are.

## 5. Bound scope and trust

### Scope

- Keep `open`, `open scoped`, `attribute`, local instances, and option changes as narrow as the
  code allows.
- Use `classical` or `noncomputable` only where genuinely required, scoped locally, with a
  surprising nonconstructive dependency documented.
- Use type classes for coherent reusable structure, and explicit arguments for local data.
- After elaboration, confirm the declaration gained no stronger hypotheses, unwanted instance
  requirements, or unnecessary nonconstructive dependency.
- Resolve every warning and linter finding the change introduces. Verify pre-existing output from a
  required check against a known baseline and report it as inherited; without a baseline, or where
  policy requires the gate green, it blocks until the responsible owner accepts a waiver.

### Trust

Pick the proof technique by the declaration's assurance boundary:

- **Kernel-checked proofs** within the declaration's approved axiom baseline are the default for
  reusable and load-bearing theorems. `decide` stays inside the kernel.
- **`native_decide`** trusts the compiler: older toolchains record `Lean.ofReduceBool`, newer ones
  mint an auditable axiom per invocation. It also trusts the runtime and every `@[implemented_by]`
  or `@[extern]` substitution, which `#print axioms` cannot see. Use it only where the local trust
  policy accepts the native path, typically in tests and private computation witnesses, and trace
  whether a private witness feeds a load-bearing value: visibility does not contain trust.
- **Placeholders** (`sorry`, `admit`) never appear in finished authored code; `sorryAx` in an axiom
  inventory is a failure. Add an `axiom` only when the specification names that assumption and
  requires it disclosed.

Audit each changed trust-bearing declaration with `#print axioms Fully.Qualified.name`,
`Lean.Util.CollectAxioms`, or a project checker documented to compute the equivalent transitive
inventory; the model workspace's `*Tests` modules pin inventories with `#print axioms`. Take the
baseline from an explicit trust policy or checker, never from existing use or passing tests. With
no baseline, compare an existing declaration's inventory before and after the change and reject new
dependencies unless the specification approves and documents them. A new trust-bearing declaration
carries no axiom dependency until its assurance boundary is stated. Compiler-trust dependencies
(`native_decide` axioms, `Lean.trustCompiler`, `Lean.ofReduceBool`, `Lean.ofReduceNat`) and custom
axioms need explicit policy approval; `Classical.choice`, `propext`, and `Quot.sound` are judged
against the declared boundary.

This step is complete when the declaration's assumptions and trust dependencies are deliberate,
audited, visible at the relevant boundary, and no wider than necessary.

## 6. Verify with Lean

Lean, not inspection, decides validity.

1. Build the smallest affected target in the owning workspace after each logical change.
2. For new or materially changed observable behaviour, add or update an executable regression with
   positive and relevant failure cases. It lives in a test root that `lake build` checks, as the
   `*Tests` libraries here do with `example`, `#guard`, and `#guard_msgs`; an unchecked Markdown
   fence is not a regression. A proof-only refactor that preserves statement and behaviour needs no
   new test.
3. Run the focused tests or checked examples for the changed behaviour.
4. Run the build, test, format, and lint commands of every affected workspace, plus any
   repository-level generation or regression gate the workspace documentation names for the changed
   surface. For `model/`, these are the targets listed in [model/README.md](../model/README.md).
5. Inspect warnings, unused imports, axiom-audit output, and unexpectedly slow elaboration.
6. Re-read the changed theorem statements and public APIs independently of their proofs to catch
   accidental changes in meaning or generality.

An implementation is complete when Lean has checked every changed declaration and every applicable
gate passes, except a verified pre-existing failure handled by project policy or an accepted
waiver. A review is complete when the non-mutating checks have run and any unexecuted authoring
checks are reported.
