# Outline for cmp/<lang>/WALKTHROUGH.md

Audience: an engineer who has never seen Umpire, model-based testing, or this sample. They know
Temporal at a user level and can read code in general, but may not know this language. Scope: the
standalone activity Model only (`standalone_activity.*` and whatever framework and worker code it
depends on). Do not walk through the Nexus Model.

Goal: after reading, the reader understands every concept and how this implementation realizes it,
and could extend the Model with a new action. Not exhaustive: show the smallest excerpt that makes
each point, quoted verbatim from the sample's files with the file name and line range above each
block. Where the framework body is sketched or elided, say so plainly and describe what it would do.

Style: short sections, one idea per paragraph, plain sentences. Explain language features the first
time they appear (e.g. "a sealed interface is...", "`syntax-parse` is..."), in one or two sentences.
No em-dashes. Length target 400 to 700 lines of Markdown including code.

Use exactly these sections, in this order, with these headings:

1. **What this is.** Three or four sentences: the rulebook/playthrough/referee picture; what a
   standalone activity is (an activity started directly with `StartActivityExecution`, no workflow,
   writes no history events, observed through `DescribeActivityExecution`); what this file does.
2. **The language in five minutes.** Only the features the walkthrough relies on, each with a
   two-line example from the sample.
3. **Vocabulary: entities, parties, actions, inputs.** The `activity` entity; the parties; `start`,
   `attemptStart`, `attemptResult`, `control`, `workerStop`; what an action class is (show how
   `AttemptResult` yields four classes and `control` four). How a fault is just an action. How the
   language represents a finite input domain with payloads (`failed(retryable)`).
4. **State.** `ProductState` and `ProtocolState`; why every field is finite; how the framework
   enumerates all 9 and 288 states (show the enumeration mechanism, e.g. derive, macro, reflection,
   `instances`, `Values()`); the `attemptBound` and saturating counter.
5. **Step functions.** The shape `(state, inputs) -> list of (outcome, next state, facts)`; empty
   list means not enabled. Walk through the product `attemptResultStep` arm by arm, then the
   protocol `protocolAttemptResultStep` and explain why it dispatches on phase as well as result
   (the three source phases react differently to a retryable failure, mirroring CHASM
   `TransitionRescheduled` / `TransitionAttemptFailedWhilePauseRequested`). Show how exhaustiveness
   is enforced (compiler, linter, macro, or not at all).
6. **The machine and its table.** The machine declaration; starts, ends, timers, unobservable,
   evidence, steps. How the framework turns step functions into the finite table and when (compile
   time, load time, test time). What evidence lines mean for a system with no history events.
7. **Two levels and the refinement.** Why a product and a protocol machine; `productOf` including
   `pauseRequested -> started`; the refinement rule (stutter or matching product row; mention the
   stricter Lean rule if relevant to this language); where the check is implemented and when it runs;
   one concrete row walked through by hand (e.g. protocol `started -> backingOff` on a retryable
   failure maps to product `started -> scheduled`).
8. **Properties.** Same-step (`completes`, `retryCompletes`) versus transition claims
   (`terminalIsFinal`, `pausedIsNotDispatched`); how each is written.
9. **Scenarios and limits.** `retriedThenCompleted` and `pausedThenCompleted`; how classed actions
   are spelled; limits.
10. **Queries.** Find versus verify; `retry` and `pauseHolds`; what the search does and where it
    runs (or that it is sketched); what an author sees when a query fails.
11. **Sets.** Functional, canary, exploratory; driven versus observed; why no `repeat` (CHASM only).
12. **Composition with the worker.** The worker machine, `activityWorker` restriction, the `sync`
    lines, `startedByPollingWorker`, what the composed claim proves.
13. **Pins.** Two or three pins from the test file and what each guards.
14. **From model to running test.** What happens after this file: Case lowering, realization (none
    exists yet for standalone activities; say so), the Go Testpilot runtime, verdicts. Keep it to one
    short section; for non-Lean languages be explicit that this layer is not in the sample.
15. **Gaps and gradual growth.** Where this Model says "not modeled" (reset, heartbeat, stutters,
    empty steps), and how that supports growing the model gradually.
16. **Mental model recap.** Five to eight bullets.
17. **Where this implementation is weak.** Two to four honest bullets from `cmp/.eval/<lang>.md`
    that a reader should know before trusting the code (e.g. compile errors a reviewer found).

Before writing, re-read `cmp/SPEC.md` (note both revision notes), your sample's files, and
`cmp/.eval/<lang>.md`. Quote code verbatim. If the reviewer found a bug in a snippet you quote,
either fix the sample file first or note the bug under the snippet.
