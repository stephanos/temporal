# Umpire IR schema consolidation research

The useful first change is to split `ir.proto` by responsibility while preserving its messages and field layout. Most apparent duplication with Testpilot represents the boundary between a symbolic Model and one executable Case. There are small genuinely shared leaves, but replacing the realization with a Testpilot Program, or merging their value languages wholesale, would lose information or move lowering into the lifter. The architecture explicitly describes the two artifacts and their separate authority. [model/README.md:117](../model/README.md#L117), [UMPIRE4_SPEC.md:131](UMPIRE4_SPEC.md#L131)

This note examines the current local schemas, Scala lifter, Go consumers, seven checked-in Model IR files, and relevant fixtures/tests. Corpus counts below count serialized entries, including declarations repeated across IR files; they are not counts of unique authored declarations. No implementation, regeneration, or test execution was performed.

It has 24 named step constructs, 20 expected Runs, and two exploration declarations. These are active vocabulary, not speculative schema placeholders. **What duplicates Testpilot, and what does not.** There is no `ProtoType` or `Guard` message in the current Umpire schema. The relevant types are `TypeRef`, `Proto`, `ProtoValue`, and `Operand`; a Run Event guard is a restricted use of `Operand`. Its common type checker is the Go `realization.TypeOf`, and `GuardProblem` supplies the shared guard restrictions. [ir.proto:82](../proto/internal/temporal/server/api/umpire/v1/ir.proto#L82), [ir.proto:963](../proto/internal/temporal/server/api/umpire/v1/ir.proto#L963), [operand.go:45](../tools/umpire/realization/operand.go#L45), [payload.go:78](../tools/umpire/realization/payload.go#L78)

| Candidate | Actual relationship | Assessment |
| --- | --- | --- |
| `RequiredSetting` | Both schemas declare exactly `key = 1`, `value = 2`; lowering copies them field for field. | Genuine small duplicate; a possible shared leaf after an explicit dependency decision. |
| `AttemptNumbering`, role kinds, expected disposition/cleanup | Same concepts, but Umpire retains positions or its own declaration shape and enums. | Sharing selected enums/data is possible; savings are small and diagnostics must remain. |
| `Proto` / `ProtoValue` versus Testpilot `Value` | Umpire contains named fields, role references, and fixture-dependent names. Testpilot values contain concrete typed protobuf messages, canonical integer strings, bytes, maps and lists. | Retain the template/concrete boundary. A Testpilot literal cannot directly replace an unresolved template. |
| `Operand` versus Testpilot `Expression` | Boolean/path operations largely correspond; learned names become Slots, fixture names become text, and reference contexts differ. | Best substantive candidate for a focused reuse investigation, but not a drop-in schema alias. |
| `Realization`, `Script`, `Command` versus `Program`, `Entrypoint`, `InstructionNode` | Realizations bind action classes to commands, select path-dependent items, derive waits, describe evidence and server steps, and retain source positions. Programs contain the selected executable graph. | Keep the distinct artifacts and lowering step. |
| Umpire `Expr` / `Value` / `TypeRef` versus Testpilot expressions and values | Finite sum/product types, pure functions, patterns, closures, channels and holes versus runtime protobuf values and execution references. | Different languages; merging them would enlarge both interpreters and blur their authority. |

Even the operand overlap has meaningful edge cases. Testpilot's empty `all` evaluates true, whereas Umpire's Run Event guard rejects an empty conjunction. Testpilot expressions expose more comparison operators and more reference contexts, and its path language includes map lookup and presence selectors beyond the lowering's supported path subset. Umpire carries an operand position and permits fixture-dependent literal names, which lower to concrete text. Reusing Testpilot expressions would still require a restricted admission layer, symbolic substitution, preserved diagnostics and consistent offline guard evaluation. The current module map explicitly allows Umpire IR only protobuf support and says “no Testpilot schema dependency added.” Directly importing Testpilot `program.proto` for one leaf would also import its program/instruction dependencies. Sharing is therefore an architectural change, not routine deduplication. A neutral leaf package is an alternative, but moving several declarations and generated APIs to save a few fields is unlikely to repay its cost. This note recommends neither dependency change as part of the initial split. **Suggested file boundaries.** Keep the current package, Go package, Java package, message/enum full names, fields, numbers, oneofs, comments and ordering inside messages. Keep `ir.proto` as the root containing `Model`. Nine files give reasonably sized units without changing the language:

| File | Declarations | Local imports |
| --- | --- | --- |
| `common.proto` | `Position`, `Empty` | None |
| `value.proto` | Finite type declarations, `TypeRef`, `Param`, `Value` and enum/record/list values | `common` |
| `expression.proto` | `Function`, `Expr`, expression nodes and patterns | `common`, `value` |
| `machine.proto` | `Action`, `Example`, `Machine`, refinement, channels, monitors, assumptions, holes, composition and `ActionClass` | `common`, `value`, `expression` |
| `claim.proto` | Properties, scenarios, queries, exploration, expectations, limits and progress | `common`, `expression`, `machine`; protobuf wrappers |
| `operand.proto` | `Operand`, its operators, `Proto`, `ProtoValue`, maps and `Name` | `common` |
| `script.proto` | `Script`, activations, `Item`, `Performance`, `Command` and instruction/read/assignment helpers | `common`, `machine`, `operand` |
| `realization.proto` | `Realization`, roles, learned/observed declarations, evidence, controls, correlation and API behavior hints | `common`, `machine`, `operand`, `script` |
| `ir.proto` | `Model` | `value`, `expression`, `machine`, `claim`, `realization` |

These are declaration dependencies, not speculative new package APIs. Their graph is acyclic: the model chain is `common ← value ← expression ← machine ← claim`, the realization chain is `common ← operand ← script ← realization`, with `script` and `realization` also importing model classes from `machine`; `ir` imports the roots it contains. `ActionClass` stores an action name rather than an `Action` message, so it can be extracted further later if avoiding that file dependency becomes valuable. Keeping its current grouping is simpler initially. [ir.proto:508](../proto/internal/temporal/server/api/umpire/v1/ir.proto#L508), [ir.proto:1044](../proto/internal/temporal/server/api/umpire/v1/ir.proto#L1044)

A declaration-only move can preserve protobuf message bytes, ProtoJSON and generated message package names. It changes file descriptors and generated file-level identifiers. ScalaPB already uses `flat_package`, so its generated message packages need not change. The implementation must update the gate to generate and hash every schema file, the stale-Go check to cover every output, Make prerequisites, the linter path exemption, and the descriptor regression test to compare the complete relocated declaration set. Merely adding imports to the old root will not generate all imported Scala files. Preserve the existing schema/wire assertions rather than deleting the test because its single-file assumption stops holding. **Metadata should be kept distinct from behavior.** `Construct.choice` names nondeterministic alternatives; `Query.exploration` selects executable candidate variations. They are not duplicate choice systems. The first is deliberately inert for behavioral identities but is reported by rows and checked by the Quint agreement; the latter changes exploration. `Property.origin` preserves capability-law attribution even though production snapshots currently omit it. `Query.total` is recomputable but intentionally asserts the lifter's count against the independent reader. `expected_run` is an explicit expected Contract and Model assessment, not a second Query answer. Removing any of these would remove diagnostics, admission checks, authoring support or live-test intent. [SEMANTICS.md:221](../model/SEMANTICS.md#L221), [ir.proto:594](../proto/internal/temporal/server/api/umpire/v1/ir.proto#L594), [origins.go:8](../tools/umpire/ir/origins.go#L8), [totals.go:37](../tools/umpire/ir/totals.go#L37), [SEMANTICS.md:873](../model/SEMANTICS.md#L873), [agreement.go:199](../tools/umpire/export/agreement.go#L199)

**What Quint suggests.** Quint v0.33.0 has seven expression variants: name, bool, int, str, application, lambda and let. A typed opcode/application form covers many operations that Umpire represents as separate message nodes. Quint also separates source locations into a map. These are useful design comparisons, not evidence that Umpire's domain declarations are unnecessary. An opcode node could shorten the expression schema, but preserving Umpire's lazy evaluation, hole propagation, pattern bindings and named-choice attribution would require a substantial compiler/interpreter migration. File extraction and shared traversal helpers are lower-risk first steps. A source-position table primarily reduces repeated artifact data, not the number of semantic concepts. [Quint expression IR](https://github.com/quint-co/quint/blob/v0.33.0/quint/src/ir/quintIr.ts), [Quint parser/source map](https://github.com/quint-co/quint/blob/v0.33.0/quint/src/parsing/quintParserFrontend.ts), [Umpire evaluation semantics:46](../model/SEMANTICS.md#L46)

**Existing general-purpose protos.** There are useful leaf replacements, but no general-purpose schema that replaces this whole IR while preserving its declared semantics.

| Existing type | Where it could help | Recommendation |
| --- | --- | --- |
| `google.protobuf.Empty` | Replace Umpire's own empty marker message. It is already imported elsewhere in the repository. | Good small cleanup. Keep each containing oneof arm: its identity still distinguishes bool/int types, controller activation, cancellation, and other meanings. Empty payload bytes remain empty; generated field types and descriptors change. |
| `google.protobuf.Duration` | Replace explicitly named millisecond timeout/interval fields. | Include in the schema migration. Standardize elapsed-time quantities on `google.protobuf.Duration`; preserve field-specific default/zero behavior and validate range, sign and required precision. This changes generated APIs and serialized artifacts. |
| `google.protobuf.Any`, existing Temporal messages | Concrete payloads and commands. Testpilot already uses both. | Continue existing reuse. Umpire's `Proto` is a template containing role references and per-Case names; substituting `Any` alone loses those. An `Any` base plus symbolic patches is possible, but adds another representation and a patch contract. |
| `google.protobuf.Struct` / `Value` | Superficially resembles a generic record/value tree. | Poor fit. Its numbers are doubles; it lacks the integer, byte and enum distinctions these schemas preserve. Exact finite-model values cannot be replaced by JSON-shaped data. |
| `google.protobuf.Type` / descriptors | Describing protobuf messages. | Already appropriate for protobuf reflection, but not a replacement for finite sum/product domains, integer ranges and channel types. |
| `google.protobuf.SourceContext` / `FieldMask` | Source metadata and field paths. | Neither matches. SourceContext supplies a filename without the line; FieldMask expresses field selection, not the indexed/map/presence path language used here. |
| `cel.expr.Expr`, `Constant`, `Value` | A standard expression AST, primitive constants and runtime values. | Adopt `cel.expr.Expr` and native CEL evaluation for runtime predicates; this direction is accepted. Prototypes support this direction. Do not automatically replace domain values/types with CEL `Value`; domain admission remains necessary. |

CEL's AST has calls, selections, aggregate construction and comprehensions, but no dedicated Umpire pattern-match, lambda, channel, hole or named-choice forms. Encoding those as custom calls would retain a custom language. Its runtime value enum representation carries a type and numeric value, while Testpilot preserves enum spellings. Adopting an evaluator requires classifying differences in missing values, errors, short-circuiting and numeric behavior as intentional semantic changes or regressions; exact equivalence is not inherently the goal. The completed investigation recommends a restricted CEL AST for realization/runtime predicates. Standard representation and tooling reuse justify this direction independently of immediate interpreter deletion. Finite model expressions should remain separate. **Accepted CEL direction and prototype evidence.** Adopt canonical `cel.expr.Expr` and native CEL evaluation for runtime predicates, with typed domain bindings and a restricted AST admission layer. The user accepted both schema and engine adoption following the prototypes; remaining semantics and integration questions are migration work. Both Umpire and Testpilot can depend on this neutral schema without importing each other. Keep symbolic template resolution, reference authority, captures, paths and ownership at their domain boundaries. [Detailed investigation and runnable prototype locations](UMPIRE_CEL_RUNTIME_RESEARCH.md).

The throwaway prototypes translated, serialized and compiled **358/358 expression roots from 20 checked-in Cases**, including 102 predicate sites. Across 1,346 synthetic evaluations, compatibility guards/ordered conditionals produced zero differences against the existing evaluator with domain reads replaced by Slots; native operators produced 153 missing-binding differences. Scala↔Go protobuf/ProtoJSON round-trips, source diagnostics, restricted AST admission and cost-limit enforcement also passed. This establishes strong confidence in representation reuse, not full domain equivalence: real path resolution, correlated facts/captures and online/offline event replay remain unproven.

Prefer standard CEL semantics where our current behavior is incidental. In particular, reconsider missing comparisons, NaN equality, enum alias equality and Boolean error handling explicitly rather than preserving quirks by default. Preserve supported capabilities and migrate artifact identities deliberately. CEL-Go v0.32.0 currently loads the older `google.api.expr.v1alpha1` AST types; the prototype successfully bridges canonical protobuf bytes at that boundary for the restricted nodes. Keep that conversion isolated and reject unsupported fields before conversion. These decisions and limitations are recorded in the [CEL report](UMPIRE_CEL_RUNTIME_RESEARCH.md).

**Priority and preservation evidence.** First split the file, retaining all existing declarations. Replace the custom empty marker separately if desired, and include `google.protobuf.Duration` conversion in the planned schema migration. Then pursue the restricted CEL AST migration with a real domain-binding/replay prototype. Consolidate traversal only where it will survive that migration, and evaluate narrowly shared leaf concepts where a demonstrated maintenance problem justifies them. Defer generic opcode consolidation, shared runtime/model values, source-table rewrites and removal of unsupported declarations. No deletion of current functionality is supported by this investigation.

The schema calls itself an internal wire with no compatibility promise, but artifact identities are real compatibility boundaries. Exploration and Model assessment hash deterministic protobuf bytes after specific metadata projections. Recorded Runs identify the exact Case by the hash of its canonical bytes; historical records must retain their matching Cases. A split should demonstrate identical lifted JSON, deterministic Model bytes, generated Cases, semantic results and artifact identities. Actual schema consolidation may change those hashes and needs a deliberate artifact migration. The existing schema tests, model gate and Go tooling/Testpilot suites are the relevant verification surfaces; the research did not run them or claim them passing. **Recommended changes, in priority order.**

1. **Split `ir.proto` into the nine files listed above.** Preserve packages, message names, field numbers, oneofs, comments and field ordering. Keep `ir.proto` as the `Model` root and preserve the acyclic import graph. This is the highest-confidence improvement and requires no functionality removal.
2. **Update generation and verification in the same change.** Make ScalaPB generation, schema hashes, stale-output checks, Make prerequisites and lint configuration cover every new file. Adapt descriptor tests to the complete schema while retaining their wire assertions. Regenerate Go and Scala outputs, run the model gate and relevant Go tests, and require unchanged Model JSON, generated Cases and artifact identities for the split.
3. **Replace the custom `Empty` with `google.protobuf.Empty` in a separate cleanup.** Preserve each containing oneof arm and update generated callers and descriptor expectations. Verify that the substitution preserves serialized messages and behavior.
4. **Migrate time durations to `google.protobuf.Duration`.** Inventory timeout, interval and elapsed-duration fields in Umpire and the corresponding Testpilot representations; convert quantities that represent elapsed time, keeping timestamps, counts and logical-step bounds distinct. Preserve each field's absent/default/zero meaning, permitted signs and bounds. Require whole milliseconds where existing consumers need them; reject unsupported precision and overflow rather than silently truncating. Update Scala authoring/lifting, Go lowering/runtime consumers and generated APIs together. Replacing an integer with a message is not wire-compatible: use new field numbers and reserve retired numbers, or introduce an explicitly versioned schema/artifact conversion. Regenerate affected IR/Cases and identities, preserve historical Case/Run pairing, and test round-trips, defaults, precision and boundary values. Keep this semantic migration separate from the declaration-only file split.
5. **Adopt CEL's standard AST and native evaluation for runtime predicates.** Reuse `cel.expr.Expr` with typed domain bindings and a versioned restricted environment. Standard schema/tooling reuse is valuable independently of code deletion. Keep finite model `Expr` and symbolic payload construction separate; do not indiscriminately replace runtime values or types. Use standard CEL operator semantics by default, with deliberate migration of missing-value, numeric and Boolean behavior. Preserve an exception only where a concrete domain requirement justifies it; engine adoption is no longer an open decision.
6. **Resolve migration details and complete domain integration before rollout.** The [throwaway prototypes](UMPIRE_CEL_RUNTIME_RESEARCH.md) establish Scala/Go interoperability and corpus expression compilation. Next exercise authoritative descriptor/path binding, symbolic lowering, correlated facts/captures, and the same real event data online and offline. Preserve source diagnostics, reference restrictions and bounded execution. Resolve error-to-verdict mapping, presence/projection, enum admission, correlation and resource budgets as specified in the [remaining migration decisions](UMPIRE_CEL_RUNTIME_RESEARCH.md). Pin the CEL environment, isolate the canonical-to-legacy loader conversion, and version/regenerate artifacts without reinterpreting historical Cases. Consolidate traversal and remove duplicate checking/evaluation as CEL takes ownership; avoid investing in helpers that the migration immediately replaces.
7. **Evaluate shared leaf types only where duplication causes maintenance problems.** Start with `RequiredSetting` and overlapping disposition/cleanup enums. A neutral shared schema would need an explicit ownership decision; avoid adding a Testpilot dependency to Umpire just to remove a few fields.

Defer a Quint-style generic operator node and source-position tables until there is a concrete benefit beyond fewer schema lines. Preserve the distinction between Models, symbolic realizations and executable Cases. Do not remove a feature solely because it is absent from current production IR: require evidence across authoring, consumers, fixtures and supported semantics.
