## Goal & Context

If the Scala checker runs as a native binary beside the Testpilot Driver, the Driver can ask it directly whether an observed step is explained and what the claims say. The Case then needs no verification content at all: no Contract clauses lowered from Properties (fn-203 R3), no conformance descriptor (fn-204), and no bound on passive observation. The cost is that a Case is no longer self-contained; running it needs the oracle binary of the matching Model version. Whether that trade is available depends on one engineering question: can the checker be built as a native binary at all. This spike answers it for three targets, GraalVM native-image, Scala Native and WebAssembly, with a go/no-go that re-cuts fn-203.3 and fn-204 on go. It is filed before fn-203 so the hard work follows the decision.

## Architecture & Data Models

- The known blocker on both targets is the claim-section rewriter, which rewrites bytecode at class-load time to give claim blocks their sectioned evaluation. GraalVM forbids load-time rewriting unless it moves to build time; Scala Native has no bytecode. The first task asks whether that rewriting can be a compile-time macro or a plugin phase, which would open both targets.
- GraalVM route: build the checker plus one sample suite with native-image, supply reachability metadata for any `java.lang.reflect` use, and measure binary size, startup and a Bank `verifyAll` against the JVM numbers in the measurement note.
- Scala Native route: cross-build the checker and one sample with Scala Native, with ScalaPB runtime's native artifact, replacing any reflection or bytecode dependency; same measurements.
- WebAssembly route: build the checker and one sample with the selected standalone scala-wasm fork, pinned to an exact commit, unless the initial GraalVM WASM availability/standalone-host probe establishes the owner's preferred replacement. Verify ScalaPB and actual checker dependencies rather than assume JavaScript-host libraries work. Load the real module through wasmtime-go with gc, function-references and exceptions, beside another module in the same store, and measure 100,000 in-host calls. Restore the oracle to the prior simulation point by an owner-approved R3c mechanism; whole-store cloning is optional. TeaVM over JVM bytecode is a fallback probe only; Scala Native to wasm32 is not attempted.
- Target end state on go (owner, 2026-10-18): Go is act-and-observe only, Scala is decide-and-judge. The adapter protocol is the fuzz bridge generalized to every run: the Model side issues one instruction at a time (`next`), the Go driver executes it against the real system and returns observations with their correlation keys (`observe`), and the Model side judges. No Program interpreter, Contract evaluation, evidence policy or assessment remains in Go; `common/testing/testpilot` shrinks to the driver and the adapter, and another system is a new driver. The Case survives as a frozen export for CI and regression. The spike measures each target against this end state, including the per-step round-trip cost (sidecar) versus in-process calls (wasm), how the live Go tests and the canary launch and pin the oracle, and where the driver's read-completion predicates evaluate without a round trip.
- Go/no-go follows the latest snapshot revision: native-image is the live target and can serve simulation synchronously if deterministic restoration and measured latency fit. WASM is preferred for simulation latency and packaging, not required for correctness. Report each hosting's evidence and consumer suitability independently. Scala Native is a conditional live fallback, not a mandatory third successful build. Applicable go recuts fn-203.3/fn-204/fn-202 planning to Model-decides/Go-acts without dropping the descriptor alternative for an unsupported consumer. No-go preserves concrete evidence and the corresponding existing route.

## API Contracts

- The main native-checker spike design note and linked per-target companion notes record build recipes, resolved/unresolved blockers, size, startup, Bank `verifyAll` wall time and recommendations. Every oracle hosting records its R3c restore mechanism; WASM records in-host latency and native-image synchronous per-step round trips, with actual comparisons where reachable. Package-only or trivial-host checks never establish real checker execution. Historical measurements remain distinct from matched local controls.
- The spike produces no production code; a macro or plugin replacement for the rewriter, if proven, is filed as its own task on fn-196 or fn-199 before any target is adopted.

## Edge Cases & Constraints

- Measurements use the measurement note's worlds and flags so they compare with the JVM rows.
- A target that builds but refuses a sample Model is a no-go for that target, with the refusal recorded.
- Nothing is downloaded into the user's home; toolchains are pinned through mise or the framework build directory.

## Acceptance Criteria

- **R1:** The rewriter question is answered with evidence: either a working compile-time replacement for the claim-section rewriting on one sample, or a recorded reason it cannot be done. Errors: none beyond the recorded outcome.
- **R2:** A GraalVM native-image build of the checker with one sample either runs `verifyAll` with the JVM's verdicts and recorded measurements, or the blocking failure is recorded. No error surface beyond that.
- **R3:** Under the owner's conditional-fallback decision, record whether a Scala Native live-sidecar probe is needed after the required target outcomes. If needed, its checker/sample build either runs `verifyAll` with JVM verdicts and measurements or records the blocking failure. If not needed, record it as untested, never a portability success. No error surface beyond that disposition or recorded failure.
- **R3a:** A WebAssembly build of the checker with one sample either answers `rows(state)` from a Go host with the JVM's verdicts and recorded module size, load time and call latency, or the blocking failure (host shim, GC support, rewriter) is recorded. No error surface beyond that.
- **R3b:** (2026-10-18, the simulation is WebAssembly; revised the same day) The module loads in wasmtime via wasmtime-go beside a second module in the same store, with the GC and exception-handling proposals enabled; per-call latency is measured at exploration scale (10^5 calls). Errors: a host that cannot enable GC or exceptions is recorded as the blocking failure, never worked around with a non-Scala build.
- **R3c:** (2026-10-18) Every oracle hosting (wasm module, native-image sidecar) restores to a prior point consistently with the simulation's snapshot: either the host snapshots the store, or the oracle answers `snapshot() -> id` and `restore(id)` over its immutable state values; after restore it answers identically to a fresh replay of the same prefix. Per-step round-trip latency for the sidecar is measured against the in-host call. Errors: a restore to an unknown id refuses; a divergence after restore is a defect, not a hosting limitation.
- **R4:** The design note states hosting results, independent live/simulation suitability, the conditional fallback disposition and one consumer-aware recommendation. Applicable go recuts fn-203.3/fn-204 and fn-202 planning to the adapter route and updates MILESTONES' Phase 5 row; mixed/no-go preserves the unsupported consumer's route and exact blockers. A synchronous sidecar is eligible for simulation when R3c restoration and measured exploration-scale latency support it; WASM remains preferred, not mandatory. No error surface beyond the recorded outcomes.

## Boundaries

- No production oracle protocol implementation; task-owned experimental snapshot/restore and timing interfaces are admitted only to prove the hosting contracts.
- No change to fn-203 or fn-204 before the decision.
- No production build target is added to the framework check.

## Decision Context

2026-10-18, phase renumbering: the owner inserted Phase 3 "Temporal Models native" (re-enable and check `model/temporal` against the final DSL) between DSL completion and the IR batch; the IR batch is Phase 4 and the one-language series (fn-199 through fn-209) is Phase 5. This spec runs in Phase 5 unless its Decision Context says otherwise.

The descriptor route (fn-204) was designed so that conformance runs without a JVM. A native binary would make the Model itself available without a JVM, which removes two of the hardest pieces of the series and the passive-observation bound at once. The three targets are tried together because they fail on different things: native-image on load-time rewriting and reflection, Scala Native on the absence of bytecode and reflection altogether, WebAssembly on the host runtime's GC support and the Scala.js host shim. WebAssembly is the highest payoff, since an embedded module restores self-contained Cases, and the lowest prior of success; the owner added it on 2026-10-18. If the rewriter can become a macro, Scala Native is the better sidecar (smaller, faster start, no closed-world configuration); if not, native-image with a build-time rewrite is the only option. Filed 2026-10-18 at the owner's request, before fn-203, so the decision precedes the work. Depends on fn-196's native checker as it stands; fn-203 and fn-204 depend on this spec.

2026-10-18, naming (owner question): Testpilot stays the runtime's name while the Case is the artifact and the Go side executes a Program; `umpire.testpilot.v1` already states it is a component of Umpire. On a go here, where Go becomes act-and-observe and the Model decides each step, the name is revisited in .4 with "driver" as the candidate (`tools/driver`, `common/testing/driver`: the adapter protocol plus one driver per system), since the Go side would no longer pilot anything.

2026-10-18, deterministic simulation (owner): the deterministic Go runtime (SCALA.md: one Go process holding runtime, Temporal and model state so a fork() checkpoint captures everything, no cross-language RPC in the exploration loop) is a future consumer of the oracle. Its needs are the spike's ranking stated precisely: the Model must be callable in-process at exploration rates and its state must snapshot and restore with the runtime's checkpoint. The WebAssembly target satisfies both (linear memory copies with the process); a sidecar process satisfies neither in a fork()-based loop; the descriptor satisfies both for bounded exploration. Add to R3a's measurements: snapshot/restore of the module's state and per-call latency at exploration scale.

2026-10-18, the simulation is WebAssembly (owner; host wasmtime / wasmtime-go): WebAssembly became the required target for the simulation on this date; revised the same day (see the snapshot revision below) to preferred, with native-image viable as a synchronous sidecar. The wasm task (.5) runs first after the rewriter question (.1); native-image (.2) and Scala Native (.3) are fallbacks for the live-deployment sidecar only and no longer gate the decision. The host binds the toolchain: the Scala.js WebAssembly backend emits WasmGC with exception handling, which wasmtime implements and wazero does not; the simulation's host choice is therefore also the Model's. The adapter protocol stays act-and-observe over pure data and becomes an in-host interface (host functions or the component model) in the simulation, NDJSON only for the live Testpilot runtime.

2026-10-18, target boundary (owner): on go, the rule is one sentence: Go executes one instruction against a system and reports what it observed; the Model decides what to do and what it means. One loop, no modes: a frozen Case is the module replaying a Program it is handed (Checker.replay), live exploration is the same loop with find/sample choosing, and offline assessment is the same loop with a driver that returns recorded observations. Go keeps only the wasmtime host, the loop, the Run recorder, the campaign coordinator and the drivers (real Temporal in Go, simulated Temporal as a wasm module, recorded Run). The instruction's read-until predicate stays data the driver evaluates locally so polling does not cross the boundary per tick. Known costs: one host call per instruction; wasmtime-go links a C library into the canary and OMES binaries; a Case runs only with its pinned module.

2026-10-18, toolchain facts (researched): the official Scala.js WebAssembly backend (stable since 1.22.0, June 2026) requires a JavaScript host and ES modules; its documentation states it does not generate standalone Wasm, and @JSExport is unsupported, so it cannot be loaded by wasmtime beside the simulation. Standalone Wasm under wasmtime exists only in VirtusLab's experimental scala-wasm fork of Scala.js (WASI and Component Model targets): about 4,000 of the 6,000 Scala.js test-suite cases pass on it (October 2025), the API is declared subject to change, Component Model support is a proof of concept with no wit-bindgen (imports and exports written by hand), JS-dependent libraries fail to link, and WasmGC programs cannot use threads. It runs under `wasmtime -W gc,function-references,exceptions`. Pure-Scala libraries over the Java standard library are expected to work, which should cover ScalaPB, but that is unverified for the checker. Consequence for .5: the target is the scala-wasm fork, not stock Scala.js; the task records which fork commit it builds against, which javalib calls the checker hits that are JS-backed, and whether the result loads through wasmtime-go with those three features enabled. Performance is unknown for a graph explorer: the stock backend reports about 30% lower run time than the JS backend on computation, no comparison with the JVM JIT exists, and Bank's 83-second JVM verifyAll is the reference workload. A no-go here is most likely a fork-maturity blocker, to be recorded with the upstreaming status, not worked around.

2026-10-18, two oracles (owner): GraalVM native-image is promoted from fallback to the live-deployment target (functional tests, OMES, canary, live fuzz): mature JDK toolchain, ScalaPB and macros compile as-is, near-JIT performance, one static binary, no cgo; it loses only the property the simulation needs, since it is a process and cannot be called in-host or snapshotted with the wasmtime store. WebAssembly stays the required target for the simulation only. Both share the compile-time rewriter prerequisite (.1). Watch item under .5: GraalVM's own WebAssembly backend (Java to WasmGC with a build-time heap snapshot, shown 2025, not yet public, standalone wasmtime status unknown); if it ships open and loads under wasmtime it is the mature compiler and the module form at once and replaces the scala-wasm fork as .5's toolchain. Scala Native (.3) remains a fallback only.

2026-10-18, execution reconciliation: .1 is integrated and closed with its bounded Bank mechanism proof, not target portability. .2 and .5 prepare in separate worktrees with disjoint target notes; compilation/toolchain use remains coordinated. The main note lives under framework design after the committed design-directory move. .3 waits for .2/.5 evidence to record the conditional fallback disposition or a necessary probe; its metadata edge into .4 is a reporting boundary, not an unconditional requirement for a third target build. The decision retains two independent outcomes. Earlier one-axis ranking, linear-memory-only snapshot assertions and stock-JavaScript-host assumptions remain historical context, superseded by the stronger current contracts and requiring actual experiments.

2026-10-18, snapshot revision (owner): co-snapshotting the Model with the simulation in one wasmtime store is a convenience, not a correctness requirement. Both sides are deterministic, so a restore needs only to put the Model back to the same point, by replaying the observation prefix or, cheaper, by the Model's own snapshot ids over its immutable state values (the checker already stores exactly those). Consequences: WebAssembly is preferred for the simulation on per-step latency and single-artifact packaging, no longer required for correctness; GraalVM native-image is viable for the simulation as a synchronous sidecar (a pipe round trip per step is deterministic, only slower), provided the adapter interface carries snapshot and restore (fn-202) and the measured latency fits the exploration volume; the simulation therefore does not hinge on the experimental scala-wasm fork. R3b is narrowed to loading and latency; R3c states the restore contract for every hosting.

Flow has no deferred status; this line is the record. MILESTONES.md was reset to the prototype alone and no longer lists this spec.
