# Gomad: shrink the qualification machinery and move the cycle driver into Rust

## Problem

The fn-232.13 size ledger (counter `gomad-source-size/v1`, `.flow/artifacts/fn232-retirement/source-size-2026-10-23.md`) puts the Rust host outside the engine at about 84k production and 23k test lines of Rust, against 51k production lines for the Go host it replaced. Around it sits a qualification pipeline that has no Go counterpart: `tools/gomad/rust/driver/` is about 34k lines of Python (roughly 20k production, 12k tests). It holds the 96-stage scheduler, stage adapters, receivers, readers, custody checks and `required-final.json` obligations. There are also about 100 Python files of parity lanes under `testdata/parity/` and a 25k-line `measurement/` module that repeats much of the same checking. Rerun the counter at start; these figures are the 2026-10-23 row.

Nobody decided to write this in Python. It started as throwaway stage scripts in `.flow/artifacts/wasm-qualification-driver/` and was moved into the product tree during fn-232.13 (commit b31b463ca5, 2026-10-22). It then grew one obligation at a time. Reviews found obligations that only re-prove other obligations, and readers that check receipts instead of behavior.

## Goal

Qualification stays at least as strong as today, with much less code:
1. **Every check catches a real failure or goes.** For each obligation, reader and receipt check, name the concrete failure it detects and show a test or mutation that it catches. Delete what re-proves another check or only checks bookkeeping. Waive no stage, bound, assertion or the one-hour limit.
2. **The cycle driver becomes a Rust `gomad` verb.** The scheduler, stage dispatch and stage readers move into the Rust workspace, as one verb that runs the cycle and validates its results. The Python driver is deleted. Unchanged leaf-command argv, assertions, bounds, resource policy and the one-hour timing policy stay the same. The inventory explicitly maps Python orchestration entry points to executable Rust replacements.
3. **The parity harness is reviewed separately.** The black-box Python parity lanes drive both binaries from outside, which is a reason to keep them out of Rust. With the Go host retired and its goldens frozen, decide lane by lane whether to keep a golden regression, fold it into Rust tests or retire a lane with replacement coverage. Preserve the independently usable frozen Go baseline and original inputs until fn-246's pending R4 and public-verb comparisons prove their acceptance.
4. **Measurement is checked for duplication.** Remove `measurement/` logic that duplicates qualify/result checking.

This implementation then proceeds without waiting for fn-232 closure, the fn-233 formal rerun, the fn-221 full sweep, fn-188 stress or fn-185 quiet-host profiles. Their outstanding acceptance stays pending with its owner. The analysis-only obligation inventory may prepare before the checkpoint. Each retained result binds to its actual commit and inputs.
- **Ordering with fn-240 and fn-246.** This spec first shrinks the machinery, ports the driver and completes focused implementation/cutover verification. Every approved fn-240 extraction and layout task follows, including the complete expanded scope. fn-246 then owns all remaining full qualification and independent receiving. It does not depend on whole fn-232 closure. No cleanup step consumes or resets the two unused full-attempt allowance.
- **Requalification transfer.** Original R6's actual full-cycle obligation remains pending in fn-246 R5-R9. Local R6/task .8 now proves the implementation and executable handoff with preserved stage-plan, genuine fixture and mutation parity. No successful fn-232.13 closing cycle exists. Failed cycles remain historical references and cannot become a green baseline; focused parity cannot replace fn-246's actual complete cycle.
- **Inventory checkpoint and R1 proof audit (owner amendment2026-10-24).** Task .1 may complete an exhaustive local inventory with verified existing catching proof, valid fold/deletion coverage or explicit mandatory retained-unproved regression contracts assigned to port tasks. Pending rows earn no R1 credit and are never keep/delete/pass dispositions. Global R1 below is unchanged and remains unproved while any proof row is pending. Responsible ports actually execute their catching fixtures. Task .7 shares R1 coverage and must audit every original source-predicate row to zero unresolved proof before deleting checks or completing cutover; task .8 follows .7 and cannot close around that audit.
- **Testing.** Golden and e2e tests come before unit tests, and a unit test must name its invariant.

## Acceptance Criteria

- **R1:** An obligation inventory exists for every `required-final.json` subgate (145 today), every driver reader/receiver module and every receipt check. Each entry names the concrete failure it detects and either its catching test or mutation, or its deletion reason. Errors: an obligation without a named failure, or a kept check without a catching test or mutation, is a finding.
- **R2:** A Rust `gomad` cycle verb replaces `tools/gomad/rust/driver/`: the same 96 stage contracts, exact unchanged leaf-command argv, explicitly mapped Rust orchestration replacements, bounds, resource policy (cores, memory, locks, scratch, live-memory guard, exclusive timing stages) and the 3,600-second limit, in serial and parallel modes, plus fresh candidate configuration composition/preparation, retained producer adapters and the kept readers/receivers as its validation step. Task .9 replaces compose/configure input construction and sealing; .10 replaces retained Python producer adapters, reusing existing Rust behavior and approved Go guest/generator/model tools. Every endpoint substitution preserves its recorded original contract and has catching executable proof; no Python bridge or placeholder producer survives cutover. The Python driver and its tests are deleted; Make, CI, QUALIFICATION.md and the determinism inventory's `driver:` evidence references point at the verb and its Rust tests. Catching fixtures also protect the global two-attempt policy across ambiguous spawn outcomes, refuse missing/mismatched enrollment bindings rather than reset history, and recheck45GiB HOST/20GiB overlay/12GiB inner resource floors immediately before reservation. Errors: a changed leaf-command argv/bound/resource declaration or an undeclared orchestration substitution fails the plan golden; a deleted check without an R1 deletion reason or a launcher policy bypass is a finding.
- **R3:** Every parity lane under `testdata/parity/` and `scripts/` has a recorded disposition (keep as golden regression, fold into Rust tests, or retire with replacement coverage), and that disposition has been carried out. Preserve the frozen Go executable/helper/source/compiler/tool inputs and raw proofs required by fn-246's actual R4/public18 receiving; disposition alone supplies no fn-232 R13 pass. Errors: a lane without a disposition, a retired lane whose checks are not covered elsewhere, or deletion of a pending consumer's required input is a finding.
- **R4:** `measurement/` logic that duplicates qualify/result checking is removed; what remains is inventoried under R1. Errors: a removed check without an inventory entry is a finding.
- **R5:** Before/after file, byte and code-line counts are recorded with the fn-232.13 counter `gomad-source-size/v1`, separating production, tests and generated code. Errors: a count without the counter version and exact revisions is a finding.
- **R6:** Focused implementation verification and an independently usable handoff prove preserved96-stage contracts/exact leaf argv/mapped orchestration/bounds/resources, supported Rust fresh-input preparation and representative genuine producer execution, the145-obligation crosswalk, genuine fixture/mutation outcomes and catching launcher-policy regressions. The handoff assigns the original actual full-cycle obligation to fn-246 after the full fn-240 scope; it records the two unused attempts, authentic original references and all pending receiving obligations. This local criterion permits implementation closure only. Original full qualification stays pending until fn-246 produces actual bound proof, with the unchanged3,600-second policy and existing timing-only deferral. Errors: invented green-baseline comparisons, a lost obligation, invalid fixture/mutation parity or administrative handoff reported as qualification success blocks completion.

## Decision Context

Owner request 2026-10-23: shrink the qualification machinery and move the driver into Rust. Python entered by accident (stage scripts promoted into the product tree in b31b463ca5) and the owner's rule since then is no new Python driver code. The parity lanes are kept out of the Rust move on purpose: they drive binaries from outside, which is what makes them a regression check rather than a self-check. Tasks come from `/flow-next:plan` once the starting point above is reached; the obligation inventory (acceptance item 1) is the first task because every deletion decision depends on it.

Owner sequencing amendment2026-10-24 supersedes the earlier closing-cycle and post-cycle-window start barriers. fn-242 implementation precedes the complete fn-240 extraction scope, then fn-246 supplies final qualification. Original R6 is transferred, not passed. Tasks .1/.2 explicitly inventory and catch three retained-launcher policy defects in the new Rust implementation: ambiguous child-spawn failure must retain its charge, absent/mismatched fixed enrollment binding cannot create a fresh history, and all three resource floors are rechecked immediately before reservation. The historical Python launcher is reference input only and is not patched by this plan. Task .4's strict reach mode consumes actual fn-246.1 proof and never waits for old fn-232.14 Flow completion.

Formal review amendment2026-10-24 assigns fresh candidate composition/preparation to .9 and retained producer replacement to .10 before .7 deletes their Python endpoints. The original argv table remains evidence; only named orchestration substitutions change, while unchanged leaf argv and behavioral contracts stay exact. A bounded fresh-input preparation/representative-production/dispatch/validation fixture proves the cutover and rejects stale or unmapped bindings. Final expensive production remains fn-246.4-owned. The existing stop_at_deadline=False policy continues evidence collection past3,600 seconds and records deferred-perf success only for an otherwise complete passing run; correctness/resource/replay failures retain their exits. Task .5 runs after possible Rust writers and records exact fold destinations.


Inventory staging amendment2026-10-24 resolves a dependency cycle found during the actual .1 inventory. Existing assertions often lack established catching proof, so requiring completed proof before the port tasks can start would require those tasks to finish before their prerequisite inventory. Task .1 now completes only exhaustive discovery and honest proof-state assignment. Its retained-unproved rows carry mandatory regression contracts and named port owners; no pending row is credited as global R1 proof. Ports produce actual executed catching evidence, and .7 audits every original row and resolves all pending proof before deletion/cutover. Both .1 and .7 advance R1, whose acceptance text remains unchanged. The initial reported145 subgates,614 orchestration sites,2138 reader sites and343 final-reader sites are discovery anchors, not a scope cap. This changes local staging only and waives no original failure, trust boundary, stage, assertion, bound, proof or final qualification obligation.

## Executable task decomposition (2026-10-24)

The source-bound inventory remains the discovery baseline. Its 3,728 checks, 145 semantic obligations, 38 endpoint substitutions and 499 function mappings are partitioned in `.flow/artifacts/fn242-cycle-proof-ownership.json` and `.flow/artifacts/fn242-port-proof-ownership.json`. These ownership maps give no proof credit. Shared validators and fixture tables should replace repeated checks at the same immutable boundary; each fold still names its original failure, surviving guarantee and executed catching proof.

Tasks .11–.15 implement the cycle primitives. Tasks .16–.52 implement bounded preparation, reader, producer and endpoint families; the port artifact's `actual_task_ids` is the exact crosswalk. Original tasks .2/.3/.4/.9/.10 retain their acceptance as integration gates. New implementations depend on primitives and other implementations. Task .2 receives genuine endpoint integration before the original reader/preparation/producer aggregate gates complete. Existing aggregate dependencies remain intact; this additive graph must remain acyclic.

Task .11 establishes shared module/type registration before parallel implementation. Successors own their declared subtrees and compile through the production module graph. Uncompiled test islands and callable success stubs are forbidden. Every assigned pending proof requires an executed intended refusal and valid control bound to original IDs and current Rust source. Task .7 audits zero unresolved proof and every endpoint replacement before Python deletion; .8 follows actual cutover. Original acceptance, cleanup order and the two unused full qualification attempts remain unchanged.
