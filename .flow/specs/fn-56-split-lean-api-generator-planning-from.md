# Split Lean API generator planning from rendering

## Overview

Separate descriptor-to-Lean normalization and deterministic naming from source emission inside the existing command package. A completed private Lean plan becomes the only input to rendering, while the command-line contract, exact artifact set, generated bytes, validation order, and publication behavior remain unchanged.

## Goal & Context
<!-- scope: business -->

The Lean API generator currently concentrates plan construction, name allocation, type validation, coordination, and source emission in one hotspot. Maintainers should be able to test descriptor interpretation and diagnostics independently from formatting and exact-byte rendering without learning a larger interface or changing generated output.

Lean consumers and operators see no observable change. Developers gain localized planner, naming, and rendering modules with focused tests.

## Architecture & Data Models
<!-- scope: technical -->

`buildLeanPlan` remains the sole interface for converting a neutral protobuf projection and generation configuration into one validated private `leanPlan`. That plan owns ordered declarations, module paths and imports, qualified names, recursive and referenced types, and the support namespace required for emission.

Deterministic naming remains part of planning but moves to its own private module. It owns scoped allocation, identifier normalization, reserved names, numeric suffixes, and digest fallback.

One pure renderer consumes only a completed `leanPlan` and returns the exact artifact map. It performs text emission and recursive Lean-type printing, but it does not inspect projections, allocate names, resolve references, reconstruct types, or interpret general generation configuration. The command coordinator explicitly sequences plan construction, rendering, artifact-map validation, and existing publication.

All modules remain private to the command package. No new Go interface, adapter, reusable package, template system, or universal renderer is introduced.

## API Contracts
<!-- scope: technical -->

- `Run` retains its existing argument contract, repeatable descriptor flag, required Lean root and output root, validation order, and error behavior.
- The generator continues to own exactly three artifacts at `<root>/API.lean`, `<root>/API/Proto.lean`, and `<root>/API/Types.lean`.
- Generated headers, module documentation, imports, declaration order, qualification, collision suffixes, formatting, artifact ordering, and bytes remain exact.
- `buildLeanPlan` returns no usable plan on failure and owns every semantic or structural decision required by rendering.
- Rendering accepts only a completed private plan and has no caller-input error surface beyond planner validity; planning failure cannot produce artifact bytes or reach publication.
- Existing filesystem containment, symlink, removal, and atomic publication behavior remain in their current owner.

## Edge Cases & Constraints
<!-- scope: technical -->

- Empty packages, duplicate identities or fields, unresolved parents, unknown named types, mismatched oneofs, unsupported scalar kinds, name collisions, invalid type shapes, incomplete imports, namespace mismatch, dependency-order violations, and service-order mismatch preserve their contextual diagnostics and fail before rendering.
- Reordered descriptor inputs, nested and cross-package references, recursive components, maps, products, options, lists, streaming methods, reserved identifiers, and digest fallback retain deterministic names and exact bytes.
- An empty projection retains its current planned and rendered result.
- Malformed descriptors or configuration, unsafe output targets, removal failures, and publication failures retain current behavior and path-specific diagnostics.
- Existing comments are preserved and move with the implementation they describe.
- At ten times the descriptor volume, the split does not add a second normalization pass, per-declaration adapter, or avoidable full-plan copy. Time and memory complexity remain the existing planning plus rendering costs.
- Crash and security behavior remain unchanged because planning and rendering stay in memory before the existing publication seam, and no CLI or filesystem authority moves.

## Approach

1. Separate private naming mechanics from plan construction, record all renderer decisions in the validated plan, and make type validation structural rather than formatting-dependent.
2. Move phase coordination beside the command runner and make rendering consume only the completed plan.
3. Reframe planner tests around normalized data and keep exact-tree fixtures as the renderer and end-to-end byte contract.
4. Run focused Go, Lean consumer, and lint gates without rewriting generated fixtures.

## Acceptance Criteria
<!-- scope: both -->

- **R1:** `buildLeanPlan` is the sole owner of package, declaration, member, and support naming; recursive dependency ordering; reference and type normalization; module planning; and structural validation. Its private result contains every decision required by rendering. Errors: empty packages, duplicate identities or fields, unresolved parents, unknown named types, missing or mismatched oneofs, unsupported scalar kinds, support-name collisions, invalid type shapes, incomplete imports, namespace mismatch, dependency-order violations, and service-order mismatch retain contextual diagnostics and return no usable plan.
- **R2:** Rendering accepts only a completed private `leanPlan` and deterministically emits sources without descriptor traversal, name allocation, reference resolution, type reconstruction, or generation-configuration interpretation. Errors: there is no user-input error surface beyond R1; planner failure produces no artifact bytes and cannot reach publication.
- **R3:** The CLI, exact three-artifact ownership, generated declarations, comments, formatting, artifact order, validation-before-publication, and byte determinism remain unchanged. Errors: malformed descriptors or configuration, unsafe output targets, removal failures, and publication failures retain existing behavior and path-specific diagnostics.
- **R4:** Focused plan-data tests and exact-tree rendering tests cover reordered inputs, collisions, nested and cross-package references, recursive components, maps, products, options, lists, module validation, streaming methods, and the empty-projection boundary. Errors: any planner diagnostic, golden byte, artifact-membership, or publication-precedence drift fails verification; fixtures are not rewritten to accept a change.
- **R5:** Every new module and declaration remains package-private and uses only existing dependencies; comments and accurate architecture documentation are preserved. Errors: an exported internal, new dependency, changed generated file, stale documentation, added drift-check target, temporary regeneration comparison, or CI workflow change blocks completion.

## Early proof point

The first task proves that plan validation and naming can be tested without source rendering and still produce the exact decisions consumed by current emission. If the plan cannot encode the support namespace, import set, and recursive type structure without leaking formatting, reconsider the plan shape before moving coordination or renderers.

## Boundaries
<!-- scope: business -->

- No public package, exported planner, new Go interface, adapter, template engine, or general renderer.
- No CLI flag, output-layout, artifact-membership, generated-source, diagnostic, or publication change.
- No new third-party dependency or generated-file ownership change.
- No broad generated-API drift verification, stale-check target, temporary regeneration/diff workflow, or GitHub Actions change.
- No API-catalog semantics; the standalone catalog spec consumes the completed generator structure afterward.

## Decision Context
<!-- scope: both — conditionally substructured -->

The normalized private plan is the deep module: it hides descriptor interpretation, deterministic naming, type resolution, dependency ordering, and validation behind one interface. Rendering remains intentionally mechanical and concrete. A reusable package or interface would add an unearned seam because this command is the only consumer.

Type validation becomes structural so the planner does not call a text renderer merely to validate data. Direct builder emission remains the established deterministic pattern; templates or a universal source generator would expand scope and risk byte drift.

Completed generator cleanup established the neutral projection and current command ownership. This split should land before the standalone API catalog work that overlaps generator planning. The previously declined broad drift-verification concept remains explicitly excluded: exact package tests and golden fixtures are sufficient for this behavior-preserving refactor.

The extra private files add minor navigation cost but improve locality. Runtime is unaffected; generator asymptotic cost, memory behavior, crash safety, filesystem authority, and security remain unchanged.
