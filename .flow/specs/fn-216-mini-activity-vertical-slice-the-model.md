## Goal & Context

After fn-210 the Rust Umpire checks Kettle natively and as wasm in a Go host, but no Temporal feature has been modelled in Rust and no Model has judged or answered a real run. The post-verdict Case slice (fn-210 R33 to R40) is broad: Testpilot's schema moves, the Model becomes the oracle, workers ask it at callbacks, five commands become one. This spec is the thinnest real slice through every boundary that slice depends on, on one feature: a standalone activity, happy path plus one failure. The Go SDK worker executes the activity for real and its function body asks the Model what to return (R37); the client observes `DescribeActivityExecution` and each observation is judged by the Model (replay: is this an admitted step from its state?). No Case, Program, Contract or CEL is involved: a Go test and a Model. The archived product-level mini activity Model (`model/archived/temporal/features/activity_mini/product/Product.scala.disabled`) is the source: one enum state, six unit actions, one safety property, fitting the Kettle-scope DSL as it stands after fn-210.19/.20.

Ordering (owner, 2026-10-19): after fn-210.7; in parallel with fn-214/fn-215/fn-213, which touch only the DSL crates; before fn-212. Amendment to R33 recorded: Testpilot's schema is neither moved, imported nor copied; the Model's Temporal vocabulary is the Temporal API.

## Architecture & Data Models

- **Boundary (owner, 2026-10-19): no Temporal detail in `model/umpire` under any circumstances.** The Temporal side of the Rust workspace is `model/temporal/`: `model/temporal/proto/umpire/temporal/v1/temporal.proto` (the extension), `model/temporal/features/activity_mini/{model.rs, temporal.rs, expected/}` (the Model, its realization, its goldens), `model/temporal/wasm/` (the Temporal guest). `model/umpire` keeps only what is system-agnostic: the Model interface core, the DSL, the checker, `umpire-wasm` as a library (ABI, buffer and dispatch of the core methods, with a hook a system guest fills with its Models and its `Any` registry), a generic `Realize<Observation, Callback, Reply>` trait (names are placeholders; the trait is generic over the extension's message types), the generic Go host (bytes in, bytes out) and the fixture runner. A gate check in `umpire-testing` fails on any mention of Temporal API packages (`go.temporal.io`, `temporal.api`, `io.temporal`) or the identifiers `temporal`/`Temporal` in `.rs`, `.proto`, `.go` and `.toml` files under `model/umpire`, allowing only the `temporalio` organization segment in module paths.
- Model: `model/temporal/features/activity_mini/model.rs` in the attribute surface. State `Model { phase: Phase }` with `Phase::{Scheduled, Started, Completed, Failed, Canceled, TimedOut}`; actors `Client { Start, Cancel }`, `Worker { Poll, RespondCompleted, RespondFailed }`, `Deadline { ScheduleToStart, StartToClose }` (internal); transitions as the archived Dispatching/Completion facets; postcondition `terminal_remains` (a closed phase is kept). Starts: `Scheduled`. No progress claim in this spec (add `path![scheduled, .., closed].assuming(fair([Worker::Poll]))` when fn-214 lands). Goldens as for Kettle, run by the same fixture runner from a `model/temporal` tests crate. `temporal.rs` implements the generic `Realize` trait for the Model: `observe(&self, &Observation) -> Vec<Action>` (status Started means `Worker::Poll` was taken, Completed `RespondCompleted`, Failed `RespondFailed`) and `answer(&self, &ActivityAttempt) -> ActivityReply`; it is the Rust counterpart of the archived `realization/MiniActivityRun.scala`.
- Model interface (owner, 2026-10-19: the proto is renamed from `umpire.oracle.v1` to `umpire.model.v1`, file `model/umpire/proto/umpire/model/v1/model.proto`, Go package and Rust module following; ABI, method IDs and message bytes unchanged; in prose it is the Model interface, never an IR). Two methods join explore/rows/refusal on the existing three-function ABI (R31/R42): `judge(Observation) -> Judgment { Explained { step } | Unexplained { expected: [Action] } }`, where the Model instance keeps its state across calls for one run and `reset` returns to a start, and `answer(Callback) -> Answer { Complete { result } | Fail { failure } }`. The Temporal extension (owner, 2026-10-19) is three envelopes over the Temporal API itself, nothing more: `Observation { method, response: Any }` (an RPC the client made and its response, e.g. `DescribeActivityExecution` and `DescribeActivityExecutionResponse`), `Callback { task: Any }` (what the SDK handed the worker, a `PollActivityTaskQueueResponse`'s content) and `Reply { request: Any }` (the RPC the worker should make, `RespondActivityTaskCompletedRequest` or `RespondActivityTaskFailedRequest`). Every payload is a `temporal.api.*` message; the Temporal guest compiles them with prost from the checked-in descriptor set `proto/api.binpb` (46 files; the Makefile already feeds it to its generators). Nothing is copied from Testpilot's proto. The core carries observations and callbacks as `google.protobuf.Any`; the Temporal guest's registry decodes, and an unknown type URL is a `Refusal`. `temporal.rs` maps RPC messages to Model actions and back (as the archived Scala realization did with `METHOD_*` constants): `observe` reads only the fields the Model models (`status` now), `answer` returns a *partial* request holding only the fields the Model decides; the SDK and server fill the rest (task token, identity, timestamps), which the realization's doc comment states so nobody expects whole-request equality. The SDK translation is the Go activity body: build the `Callback` from `activity.GetInfo(ctx)`, ask the Model, turn a `RespondActivityTaskCompletedRequest` into the return value and a `RespondActivityTaskFailedRequest` into a non-retryable `ApplicationError`; the SDK performs the real RPC. A Temporal-extension message other than these three envelopes is a review finding.
- Go host: `model/umpire/hosts/go` gains `Judge`, `Answer`, `Reset` over the core messages only (`Any` payloads pass through); the Go test loads the Temporal guest artifact built from `model/temporal/wasm`. The run's single Model instance is in-process in the test (R40's in-process case).
- Go test: `common/testing/testpilot/temporal/model_slice_test.go` (name indicative): in-process server from the existing test infrastructure, the existing SDK worker path registering one activity whose body calls `Answer`, `StartActivityExecution` via the client, `DescribeActivityExecution` polled until a closed status with every observation passed to `Judge`; two scenarios, completed and failed (non-retryable, `maximumAttempts = 1`); asserts every observation explained and the final phase as the scenario expects; a deliberately wrong observation (a mutated status) is reported `Unexplained` naming the expected actions.
- Write-up: `model/DESIGN.md` section "Mini activity slice": DSL gaps found (`end`, facts, inputs), protocol findings for the R33 redesign, the in-worker `Answer` latency, and what the Case slice can now assume.

## API Contracts

- Rust: the mini activity fixture compiles and its goldens pin report/states/rows.
- wasm/Go: `Reset()`, `Judge(obs) (Judgment, error)`, `Answer(cb) (Answer, error)` on the host over core messages, byte-identical encoding both sides; the Temporal side generates its envelopes with the existing generators and its `temporal.api` types from `proto/api.binpb` (prost) and `go.temporal.io/api` (Go).
- Go test: `go test ./common/testing/testpilot/temporal -run ModelSlice` with `CGO_ENABLED=0` and the built guest; runs in the Testpilot gate, not in `make model-check` (it needs the server).

## Edge Cases & Constraints

- The Model instance's state across `Judge` calls is per run; a second run calls `Reset`. A `Judge` after an unexplained observation keeps the Model's state (the run is already unexplained) and reports again.
- Trap/panic/refusal behaviour of the host is unchanged (fn-210 capability and panic boundaries).
- R30 holds for `make model-check` (the fixture adds a Kettle-sized Model); the Go test's own time is reported in the write-up, not budgeted here.
- Standalone activities require the server feature the repository builds; the in-process server of Testpilot's tests provides it.
