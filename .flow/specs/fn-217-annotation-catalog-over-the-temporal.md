## Goal & Context

fn-216 makes the Model speak the Temporal API (`temporal.api.*` messages in three envelopes). Those messages carry no meaning beyond their types: nothing says a field is a UUID, a timestamp, generated data or a secret; nothing says two fields are never set together; nothing says a read may trail the write. This spec adds that meaning as a typed sidecar catalog, since the API protos are upstream's (`proto/api.binpb`) and cannot carry inline options. The catalog serves four consumers: filling the fields the Model does not decide (`fill`), validating every request sent and response observed (`validate`), feeding the Model's judgment with consequences (a `Visibility` lag, a `Cached` ttl), and, the owner's key addition, mapping each rule to the error the server is expected to return, so a probe can send each violation and report mismatches between the catalog and the server: a gap analysis in both directions.

## Architecture & Data Models

- **Layering (generic in `model/umpire`, Temporal in `model/temporal`; fn-216 R5's gate check applies).** `umpire-annotations` (new crate) defines the vocabulary and the engine with no system names: `Kind` (exactly one per field: `Uuid`, `Identifier`, `Timestamp`, `Duration`, `Counter`, `Random`, `Secret`, `Enum`, `Text`, `Bytes`, with per-kind constraints named after protovalidate's, e.g. `string.uuid`, `duration.gt`, `enum.defined_only`, `repeated.unique`), `Tag` (any number per field, each with a `Consequence` the engine or the Model can act on: `Monotone`, `Immutable`, `Cached { ttl }`, `EventuallyConsistent { polls }`, `IdempotencyKey`, roles `Decided`/`Observed`/`Ignored(reason)` after AIP `field_behavior`), `Rule` on a message (JSON Schema's presence algebra only: `required`, `any_of`, `one_of`, `requires`, `excludes`; value rules belong to kinds), `Expectation` (what the system does on a violation: `Rejects { code, message_pattern, details_type }` or `Accepts` or `Unobservable`), `Catalog` keyed by fully qualified field paths, `validate(msg) -> Vec<Violation>`, `fill(msg, seed)`, and the gap report types. Temporal-specific tags (`Visibility { lag_polls }`, task-queue scoping, ...) are types in `model/temporal` implementing `Tag`; a tag moves up only when its consequence is system-free.
- **Admission rules.** A kind is checked against the prost field type at compile time. A tag declares the kinds it applies to; contradictory pairs are compile errors (`Decided + Ignored`, `Secret + Observed`, `Random + Decided`). A rule naming an `Ignored` field is refused. A tag without a consequence or a validation is not admitted; `Ignored` requires a reason.
- **Readable catalog surface (in `model/temporal`, over prost-generated API types).** `#[derive(Catalog)]` mirror structs live in `feature/<feature>/api.rs`, with shared messages in `foundation/api.rs`. Field names follow the proto exactly and kinds are field types. Exactly two helper namespaces separate server rules (`#[rule(...)]`: value constraints and expectations) from protobuf mapping (`#[mirror(...)]`: direction, roles, projections and explicit ignored reasons). Presence is one item-level algebra: `required`, `any_of`, `one_of`, `requires` and `excludes`, with each rule's expectation on the same attribute. Fields carry value rules only. Request/response roles default from the item, with `Secret` always defaulting to Decided; ignored fields retain explicit reasons. The derive and descriptor scanner share one parser. A typed `View<K>` supplies projections and fallible setters; a malformed encoded-message mutation returns a value-free generation error before replacing the field, rather than panicking or silently doing nothing. This does not change Model or Go panic behavior.
- **Build-failing exhaustiveness.** Fields use generated struct patterns without `..`; explicitly reviewed enum-value inventories in `foundation/enum_inventory.rs` are checked against the descriptor and exhaustive Rust matches; oneof alternatives use exhaustive matches. A generated `WorkflowServiceMethod` enum/table supplies RPC identities for a wildcard-free feature classification, and every Model action remains bound to an RPC, revealed by an observation, or environmental with a reason. An unknown enum integer at runtime is refused. New descriptor fields, values, alternatives or methods therefore fail until classified; neither prost's evolving `is_valid` nor existing wildcard Model matches substitute for the explicit enum admission inventory. Full mirrors, oneof alternatives and service declarations follow proto declaration order, checked at build time.
- **Expected errors and the gap probe.** Every rule and every kind constraint on a request field carries an `Expectation`, normally `Rejects { code: InvalidArgument, message_pattern, details_type }`, restated from the server's own validator. The catalog names no server internals (owner, 2026-10-21: "we're binding it too much to internals of Temporal and Go; we don't want that kind of mapping"): no `covers`, no validator identities, no `validators.rs`; the server is a black box described by its observable contract (rules, status codes, messages, limits). `Code` uses the protocol's status names. Explicit loose expectations (code-only or any non-OK status) and inherited required-field patterns remain visible and counted in gap output without leaking request, response or error contents. Rust owns violation construction and classification; Go transports each probe to the in-process server. Outcomes are `Confirmed`, `Mismatch`, `Accepted` or `Unverifiable`; `Accepted` and `Mismatch` fail unless listed in a dated `accepted_gaps` block with a reason. `gaps.txt` is the per-feature golden.
- **Reverse direction, black-box.** The probe also mutates every request field with generic mutators independent of the catalog (absent, empty, limit plus one, negative, undefined enum value) and reports a rejection no rule predicts as `Unannotated`, so a server check the catalog never mentions is visible from behaviour alone. The Go source walk over server validators (`reverse_coverage.go` and its tests) is deleted (owner, 2026-10-21).
- **Consumers in fn-216's slice**: `fill` supplies `request_id` (Uuid) and any `Random` input; `validate` runs on every request sent and every response observed in the slice test; `judge` consumes `Visibility`/`Immutable`/`Monotone` consequences when the mini activity catalog carries them.

## API Contracts

- `umpire-annotations`: `Catalog`, `Kind`, `Tag` (trait), `Consequence`, `Rule`, `Expectation`, `validate(&M, &Catalog) -> Vec<Violation>`, `fill(&mut M, &Catalog, &mut Rng)`, `GapReport`.
- `model/temporal`: `#[derive(Catalog)]` mirror structs, kind field types and `#[rule(...)]`/`#[mirror(...)]` attributes; catalog factories receive `dc::Limits`, whose defaults match the server. Generated `Inspect` and RPC dispatch traverse nested messages, oneofs, maps and repeated messages; custom `via` projections remain explicit. `#[mirror(response_checks = RawRetryPolicy)]` explicitly links the supplemental raw-response catalog without duplicating recursion or normalizing malformed response values away. Generated service identities feed an ordinary exhaustive feature classification. Shared foundation and feature mirrors coexist in one crate; the documented local-marker seam is required before splitting crates because of Rust's orphan rule.
- Probe: `make umpire-check-model-gaps`, golden `feature/<feature>/expected/gaps.txt`; no source-reading tooling remains.

## Edge Cases & Constraints

- Kinds that cannot be generated (`Secret` from outside) are `Decided` or supplied by the test; `fill` refuses a field it cannot fill, naming it.
- A response violation is a server finding (reported, never silently fixed); a request violation before sending is a Model or driver bug and fails the test.
- Redaction: `Secret` fields are redacted from Runs and reports by the engine.
- fn-210 R30 applies to `make model-check`; the probe runs in the Testpilot gate.

## Acceptance Criteria

- **R1:** Exhaustiveness at the four levels is build-failing: a field, enum value or method added to `proto/api.binpb` for an annotated message/service, or an unbound Model action, fails the build naming it. Errors: as stated; pinned by trybuild fixtures and a build-script negative control with a mutated descriptor set.
- **R2:** The layering holds: one kind per field, any tags, rules per message; the admission rules are compile errors with the messages above; kinds are checked against prost types; names follow protovalidate (constraints), JSON Schema (presence operators) and AIP `field_behavior` (roles). Errors: pinned by trybuild fixtures.
- **R3:** Every request-side rule and kind constraint carries an `Expectation` stating the observable server rejection or intentional acceptance it describes, without naming server functions; the probe sends each violation and produces the `gaps.txt` golden with `Confirmed`/`Mismatch`/`Accepted`/`Unverifiable`; `Mismatch` and `Accepted` fail unless listed with a dated reason. Errors: a rule without an expectation is refused at compile time.
- **R4:** Reverse direction, black-box (amended 2026-10-21): generic mutations of every request field report `Unannotated` rejections in `gaps.txt`; the catalog names no server function. `reverse_coverage.go` and its tests are deleted. Errors: an `Unannotated` entry fails unless listed with a dated reason, like `Accepted`.
- **R5:** The mini activity catalog annotates every message fn-216 touches (`StartActivityExecutionRequest`, `DescribeActivityExecutionResponse`, `PollActivityTaskQueueResponse`, `RespondActivityTask{Completed,Failed}Request`) and the slice test uses `fill` and `validate`; `judge` honours `Visibility` if the catalog declares it. No error surface.
- **R6:** `umpire-annotations` contains no Temporal name (fn-216 R5's gate check covers it); Temporal tags live in `model/temporal`. Errors: the gate check.

## Boundaries

- No inline proto options, no edits to upstream API protos, no CEL, no external validation engine (protovalidate's and garde's vocabularies are borrowed, not their runtimes).
- No annotation of Testpilot's own proto.
- No automatic derivation of Model transitions from annotations; consequences inform `judge`, `fill` and `validate` only.
- Does not start before fn-216.
