## Goal & Context

The Model ships as a wasm guest and Go already consults it through `umpire.model.v1` for judgment (Judge) and SDK callbacks (Answer). Testpilot, the Go test runtime, still carries roughly 20,000 generic and 29,000 total non-test lines of its own smarts: CEL predicates, contracts, verification, evaluation profiles, an IR interpreter, replay, campaigns, and generated Case trees. fn-216 proved the dumb-host shape for one activity, bespoke, outside Testpilot. This spec makes that shape the only one: Go becomes a Runner that drives a Driver, asks the Model what to send, hands every observation and callback to the Model, and records a Run. Everything that decides meaning moves into, or already lives in, the Model and its Realization inside the guest.

It discharges the post-verdict obligations R33 to R40 recorded in DESIGN.md's "Recommendation and next slices" table and retires the "Case slice" name. It follows fn-227, because proposing a request needs a world and action inputs to fill it from.

## Architecture & Data Models

- **Names.** Crate `umpire-wasm` becomes `umpire-runtime` (the export-free Model runtime: state, replay, freezing, Reset, Realize, Runtime); `umpire-tests` becomes `umpire-fixtures`. "Realization" is the one word for a Model-to-system binding; README and DESIGN prose stop saying "binding". Go: package `runner` with types `Runner`, `Run`, `Driver`; the wasm transport stays `Host`; the out-of-process worker forwarder is `Shim`.
- **Propose.** Method `METHOD_PROPOSE = 6` in `umpire.model.v1`. `ProposeRequest { uint64 seed = 1; }` and `ProposeResponse { google.protobuf.Any request = 1; string action = 2; ProposalKind kind = 3; }`; a Model with no enabled external action answers `Refusal` with a new `REFUSAL_CODE_QUIESCENT = 9`. `Realize` gains `fn propose(&self, state: &M::State, seed: u64) -> Result<Proposal<M::Action>, Refusal>` where `Proposal` is `Action { action, request: Any }` or `Bootstrap { request: Any }`; Action checks enabledness, Bootstrap follows the admission contract below. Both are pending until their final correlated Observation is Judged. Internal actions and Deadline ticks are never proposed. Determinism: the same state and seed yield the same proposal.
- **Runner (Go, `umpire.local/model/runner`).** One loop: Reset; repeat { Propose; Driver exchanges correlated observations/callbacks incrementally; serialize Propose/Judge/Answer through one Host and deliver each result back while the action is in flight } until the Model is quiescent, the step budget is spent, or a judgment is Unexplained. Exactly one `Host` (one Model instance) per Run; callbacks are serialized into it. Modes are arguments to the one loop: `question` (one Propose or Judge over a given state, no Driver), `explore` (seeds 1..n), `reduce` (shortest seed prefix reproducing an Unexplained), `replay` (a recorded Run's ordered state-changing protocol calls replayed, no Driver), `repeat` (n Runs, same seed set). One command `umpire` with those modes replaces run, fuzz, replay, assess and repeat.
- **Run.** `umpire.run.v1.Run { model_hash, protocol_version, world, seed, repeated Event events, Verdict verdict }` where an Event is one of Proposal, Observation plus JudgeResponse, Callback plus AnswerResponse, Refusal, or DriverFault (unreachable endpoint, callback timeout, read timeout without Model acceptance). The verdict is Explained, Unexplained(at event i) or Refused. No profiles, receipts, provenance, contracts or evaluation documents. `publish` stays a never-overwrite store of Runs keyed by model hash, seed and the canonical Run content hash; the canary keeps only its lease and policy.
- **Driver (Go interface).** the incremental correlated Driver contract below; plus the mechanics the Model does not own: poll interval, read timeout and backoff as instruction fields on the Observation request, capture and redaction as field paths, RPC completion and evidence well-formedness checks. The Temporal Driver is the retained `temporal/*` driver code reduced to act-and-observe over the generated API; it never parses a Temporal message for meaning.
- **Shim.** For non-Go SDK workers: a local gRPC endpoint on the Runner speaking `umpire.model.v1` Answer with a protocol version field; a thin per-SDK forwarder returns result, failure, heartbeat or delay. Unknown version is a Refusal. In-process Go workers call Answer directly.
- **Deletion.** `internal/verification`, `evaluation`, `cel`, `predicate`, the IR CEL bridge, `contract`, `casefile`, `campaign` and `replay` are removed; `internal/ir` shrinks to instruction decoding, `internal/execution` to act-and-observe; generated Case trees and the seven legacy failing tests go with them, replaced by Runner questions over the activity Model.

## API Contracts

- `umpire.model.v1`: new `Method`, `ProposeRequest`, `ProposeResponse`, `Response.propose`, `REFUSAL_CODE_QUIESCENT`; existing field numbers/codes preserved; additive bootstrap-kind and polling-feedback fields as specified below, with wire goldens. Response tag 7 stays reserved; Response.propose uses fresh tag 9 (Annotate remains tag 8).
- `umpire.run.v1.Run` as shown; it is the only artifact a Run writes.
- `Realize::propose` as shown; existing `observe`, `matches`, `answer` unchanged.
- Go `runner.Runner` with `Run(ctx, mode, opts) (*Run, error)`; `runner.Driver` as shown; `host.Host` gains `Propose`.
- `umpire` command: `umpire <question|explore|reduce|replay|repeat> --model <guest.wasm> [--seed n] [--budget n] [--run <path>]`; exit code 0 Explained, 1 Unexplained, 2 Refused or DriverFault.

## Edge Cases & Constraints

- Every existing behavioral golden, wire golden and the fn-216/fn-227 live slice keep passing across the renames; the renames land alone before any behaviour change.
- A Propose while a proposal is pending is a `REFUSAL_CODE_STATE`; a correlated final Judge that explains the pending proposal clears it; an explained intermediate poll keeps it pending; an Unexplained freezes the run until Reset, as today.
- A Driver fault is recorded as an Event and ends the Run with Refused; it is never a Go verdict about the system.
- Reduce is bounded by the original seed count and reports the shortest reproduction it found, not a minimum.
- Size: at most 5,000 generic-runtime and 11,000 total non-test Go lines in Testpilot after this spec, reported by package in DESIGN.md; the generated `v1` package is excluded from both counts.
- R30 budgets hold for `make model-check`; the Runner's Go tests join the existing Go host targets, not the Rust gate.
- No new Rust crates beyond the renames; Go stays `CGO_ENABLED=0` on wazero.

- **R2:** Propose is on the protocol, the Runtime, `Realize` and `Host`; the activity Realization proposes Start through bootstrap admission and cancel/worker responses from enabled external actions with inputs filled from the world; same state and seed give the same proposal; wire goldens pin the method. Errors: quiescent Model refuses with `QUIESCENT`; a pending proposal refuses a second Propose with `STATE`; a proposal naming a disabled action is a Runtime defect caught by a negative control.
- **R3:** The Go `runner` package runs the one loop with the five modes and writes a `Run`; one Host per Run; callbacks serialized; the `umpire` command replaces run, fuzz, replay, assess and repeat and those commands no longer exist. Errors: Unexplained ends the Run with the event index; DriverFault and Refusal end it Refused; exit codes as specified.
- **R4:** The Temporal Driver acts and observes over the generated API with poll, timeout, backoff, capture and redaction as mechanics; the live activity slice runs through `umpire explore` end to end (start, retry, completion, cancellation, host refusal) with the Runner's Run as the only artifact. Errors: a read timeout without Model acceptance is a DriverFault event judged Refused; malformed evidence is refused before Judge.
- **R5:** A Shim endpoint on the Runner forwards Answer to one non-Go SDK worker with protocol versioning; a control proves result, failure, heartbeat and delay forwarding and the unknown-version refusal. Errors: unreachable endpoint and callback timeout are DriverFault events.
- **R6:** The listed packages are deleted, `ir` and `execution` shrunk, generated Case trees and the seven legacy failing tests removed; the Testpilot umbrella is green; sizes reported by package meet at most 5,000 generic and 11,000 total. Errors: a count over target fails the task unless the owner grants an exception in writing.
- **R7:** DESIGN.md gains "Runner and Run" recording the vocabulary sentence, the protocol addition, the Run schema, the per-package line counts before and after, and timings; the R33 to R40 table rows become discharged with pointers. No error surface beyond the gate.

## Boundaries

- No new Model, no Model semantics change, no DSL change beyond what fn-227 delivered.
- No Component Model, no wasmtime for Go, no cgo.
- No remote or multi-host Runner; one process, one Host per Run.
- No Workflow, Nexus or Schedule Drivers; the Temporal Driver covers the activity slice only. Other Temporal primitives arrive with their Models.
- No new distribution of prebuilt wasm and no extraction per MIGRATE.md; MIGRATE.md's path table is updated for the renames only.
- No reintroduction of Case identity, Program, Contract, profiles, receipts or provenance under another name.

## Execution contracts resolved by the backlog review

**Bootstrap and pending state (R2).** Start is admission, not a Model transition. Add a default-false Realize capability declaring that a fresh Run needs bootstrap. In that mode Reset clears admission and pending transport state, using fn-227's transactional world-admission seam. The first Propose returns Bootstrap with a Start request filled from the selected run configuration; its action string is empty. `ProposalKind` is UNSPECIFIED=0, ACTION=1, BOOTSTRAP=2; unknown/unspecified kinds are refused by consumers. Action proposals retain exact enabled-action validation. Bootstrap is available only before admission; subsequent proposals while either kind is pending refuse STATE. Judge admits successful actual filled Start request/result from the same invocation using fn-227.12/.5 and only then installs the World and Scheduled/attempt-one state. Failed/missing/crossed evidence cannot admit a World. No Start action is added to the Model. Callback before admission is refused, never buffered as an invented Poll. Pending/admission changes commit only after response publication; Reset and failed-publication controls cover both proposal kinds.

**Incremental Driver (R3/R4).** Replace batch Act/receive-only Callbacks with `Start(ctx, requestID, request) (Exchange, error)`. Exchange supplies an Events stream and `Respond(ctx, eventID, Decision) error`, plus `Close() error`. Each event has a monotonically ordered ID and request correlation and is Observation, Callback or transport Done/Fault. Observation carries the actual request/response evidence; Callback carries its payload and a worker call correlation. The Driver waits for the event's decision before its next dependent poll/worker response. The Runner continues draining the exchange while an RPC is active and serializes all Host calls in receive order; it never waits for Start/RPC completion before answering a worker. Decisions contain the Judge response/continue flag or Answer reply, or cancellation/refusal. Duplicate/unknown IDs, wrong request correlation, closed streams without Done and responses after cancellation are DriverFaults. Close cancels and joins owned work; all sends/waits honor context deadlines. The Driver understands event mechanics and opaque instructions, not Model predicates.

**Read completion (R2/R4).** Add `bool continue_polling = 3` to JudgeResponse; absent=false preserves existing final-observation behavior. A default-false Realize method computes this after the prospective observation has been validated/replayed, from that observation and prospective state. The Runtime publishes it with the Judge result transactionally; Unexplained never continues. Only a correlated final Explained clears the pending proposal. Intermediate Explained observations keep pending and trigger another transport read after the prescribed poll delay. The current Temporal realization supplies the completion decision; Go does not inspect Temporal phase. Answer may commit its delivery path between polls without clearing an unrelated pending request. Test an intermediate Describe, intervening worker callback/reply and final Describe, plus timeout/cancellation at each wait. No additional Model transition/claim semantics are introduced.

**Run and replay (R3).** Events record the exact request and response for Reset, Propose, Judge, Answer and any Annotate used for filling, in publication order, together with request/event correlation, plus DriverFault/Refusal. Run retains model_hash, protocol_version, selected world/configuration, seed, repeated events and verdict; the revised Event list is the authoritative schema. Replay constructs a fresh same-version/hash Host, restores configuration, replays the ordered protocol calls (including bootstrap, proposal pending state and Answer delivery), and compares outputs and terminal disposition. It performs no external calls. Reject missing/reordered/duplicate events, crossed correlations, mismatched model/version/configuration and tampered responses. A real callback-bearing completion Run and the fake-driver control must replay with identical judgments. Rendering/redaction occurs after judgment; if redaction removes evidence necessary for replay, the Run is explicitly Refused for replay rather than reconstructed from guessed data.

**Modes and verdict scope (R3).** question consumes a supplied recorded prefix to reconstruct state, then makes one Propose or Judge, without Driver effects; it cannot invent an arbitrary state through Reset. explore runs bounded seeds with fresh configured Hosts; repeat creates independent executions for the same seed set. reduce tries shorter prefixes of the recorded proposal-seed sequence against a fresh Driver/Host, with a finite candidate count bounded by the original proposal count and an explicit per-run event/time budget. It preserves callback/observation handling and reports the shortest reproduction actually found, not a minimum. An Explained budget-limited Run means every observed event was explained, never that all future behavior is verified; record the budget termination reason. A DriverFault or malformed/incomplete replay is Refused.

**Publication (R3).** Use model hash / seed / SHA-256(canonical serialized Run payload) as the immutable store key; the digest is computed outside the payload to avoid recursion. Canonicalization pins protobuf ordering and excludes wall-clock logging from the payload. Identical payload publication is idempotent, a differing payload cannot overwrite, and repeats with different observations receive different keys. Test both repeats, concurrent publication, corruption and existing-file collision. The embedded artifact/freshness behavior delivered by fn-230 stays supported.

**Positive fixture (R2/R3).** Task .2 provides a small stateful control realization/guest over an existing deterministic single-start test Machine, with bootstrap, proposal, polling and callback support; no second production Model or dependency on fn-233. Extend the existing control guest infrastructure and pin its wire/native parity. Task .3 uses it with a fake Driver to cover successful runs, callback delivery, replay, reduction and failures. Stock Kettle stays the unsupported-stateful-operation control. The live activity realization remains the production integration test in .4.

**Progress and ownership (R3/R5/R6).** Batch modes emit redacted stderr progress for mode, iteration, seed, event position and termination reason; no payloads, credentials or absolute artifact paths leak into progress. Tests capture progress on slow fake-driver/reduction/repeat runs. Tasks .5/.6 share manifests/integration wiring and therefore execute serially, .6 after .5. Task .6 enumerates current dependents before deletion, maps each of the seven legacy failures to retained Runner coverage, and refuses deletion as a substitute for that coverage. Record non-test line counts for both Testpilot and the new Runner/Driver packages, so moving code outside the counted subtree cannot satisfy the size target. Generated schema code is separately reported/excluded.
