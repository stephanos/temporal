## Goal & Context

<!-- Goal & Context: 50% [user], 35% [paraphrase], 15% [inferred] -->

The framework's tests come in two kinds. Native tests build a Model in Scala and assert on Scala
values: step results, binding order, lazy initialisation, equality laws. Toolchain tests copy a
testdata tree to a scratch directory, package it with scala-cli, run the lifter, lint or check on
it, and compare what came out. The toolchain kind is where the cost sits. Only the `lifts` fixture
is golden: its IR, waivers and refusal lines are files under `expected/`, regenerated by one flag,
guarded by a leftover check and by identity contracts. Every other toolchain fixture keeps its
expectation inline in a Scala test: a substring of a diagnostic, an `intercept`, a hand-copied
JSON path. The result is three lines of test per line of source in the exporter, a fixture-to-test
mapping that lives in a hardcoded list, a diagnostic wording change that touches dozens of test
files, and a reify plugin with no direct test at all.

The owner's proposal: a test case is a folder. Its sources are the input, and its expectation is a
file in the same folder. One runner discovers the folders and compares whole files. This covers
lift, refusal, lint, compile-time refusal, inspect and the check stages that read sources, and most
inline toolchain tests go away. The lifts fixture already proves the shape works here; this spec
makes it the only shape for toolchain tests and prunes what it replaces.

The native behaviour tests stay Scala. A test that asserts `press(Switch, off)` yields one state is
a Scala value test; turning it into a fixture means inventing a scenario-script format to replace
the assertion, which is DSL vocabulary the owner has declined before. fn-195 reshapes the sample
tests as ModelSuites; this spec does not touch them.

Why now: Phase 3 re-anchors the exporter, lint and plugin against the final DSL, and the 2026-10-17
scout found the export fixtures failing wholesale on retired vocabulary. Every expectation gets
rewritten then anyway. Building the case runner first and re-anchoring into it, instead of into
inline assertions, is the one moment this migration is free. Placement in Phase 3, at the head of
the export and lint re-anchoring, is my interpretation for the owner to confirm.

## Architecture & Data Models

<!-- Architecture: 30% [user], 40% [paraphrase], 30% [inferred] -->

- **Unit.** A testdata folder that compiles as one scala-cli package: its Scala sources, a
  `project.scala`, a `README.md` that states what the unit shows, and an `expected/` directory. A
  unit is the grain of compilation; cases share a unit when they share its compile outcome. The
  `lifts` fixture today, 46 sources and one jar, is one unit; a plugin refusal that fails the compile
  is a unit of its own, since it fails the whole package.
- **Case.** One expected file. Its name says which tool runs and against what. The files present in
  `expected/` are the unit's whole contract; the runner derives the tool invocations from them and
  from nothing else. There is no manifest and no list of fixtures in Scala.
- **Runner.** One munit suite per tool. It discovers every unit under the framework's testdata,
  registers one test per case named by the unit and the file, packages each unit once, runs the
  tool, and compares the output to the expected file byte for byte after normalising scratch paths
  to repository-relative paths. A mismatch fails with a unified diff. Packaging and tool runs stay
  bounded by the existing build and lift slots so units run side by side.
- **Update.** One environment flag rewrites expected files. As today, it rewrites only after every
  unit compiled as its cases say it should and every case ran, and it refuses while a leftover or
  unknown file sits in any `expected/`. The tree it leaves is one whole run's.
- **Guards that stay Scala.** Properties of the tools that no single expected file can state: a
  declaration's identity does not move with its line, a refused lift writes no IR, update writes
  nothing on a partial run, the runner fails a unit that declares nothing. Identity contracts move
  beside the cases they guard as an `expected/identity.json` the runner checks when present.
- **What leaves.** Every inline test in export and lint whose assertion is a substring, line or
  field of a tool's output becomes a case and is deleted. The `lifts` driver, its hardcoded fixture
  list and its per-fixture `test(...)` blocks fold into the runner. The lint rules in check that scan
  framework sources keep their in-memory tests where the input is a string literal, and gain cases
  where it is a tree.
- **What stays.** Native tests in dsl and realize. The samples' tests, owned by fn-195. The
  check suites that run Go or compare interpreter tables, held for the sweep. The framework loop
  test.

## API Contracts

The layout of a unit, and the expected file names the runner understands. The files shown are the
complete set; a file in `expected/` with any other name fails the unit.

```
export/testdata/<unit>/
  README.md                       what this unit shows, one paragraph
  project.scala
  <Sources>.scala
  expected/
    <root>.ir.json                the lifted tree for <root>; from fn-201 an internal expectation of the lift module only, read by nothing else
    <root>.waivers.json           (dropped 2026-10-18: waivers are a `@gap` kind under fn-200; no file is written)
    refusals.txt                  every `lift:` line, sorted; the lift exits 1 and writes no IR
    compile.txt                   the plugin's diagnostics, sorted; the package does not build
    lint.txt                      every finding the framework lint reports, sorted; from fn-200 the native lint's findings and coverage
    inspect.txt                   what inspect prints for the unit
    identity.json                 the identity contract the runner checks against <root>.ir.json
```

`<root>` is the fully qualified name the lifter is given, as it is today
(`fixture.presence.Presence`, `fixture.hints.Hints$package$.keptBehavior`). A unit holds
`<root>.ir.json` files or `refusals.txt` or `compile.txt`, never two of the three: an admitted lift
and a refused one cannot share a run. `lint.txt` and `inspect.txt` may sit beside any of them.

The runner's one flag:

```
UMPIRE_FIXTURES_UPDATE=1   rewrite every expected file after a complete run; refuse on leftovers
```

A failure reads, in this order: the unit, the case file, the unified diff of expected against
actual with repository-relative paths, and the command that produced the actual output.

## Edge Cases & Constraints

- **Determinism.** A tool whose output order depends on hash iteration or thread timing fails its
  case intermittently. Finding and fixing such an order in the lifter, lint or inspect is in scope;
  the expected file is never sorted by the runner to hide it, except where the format is a set of
  lines (`refusals.txt`, `compile.txt`, `lint.txt`), which are sorted by the tool before writing.
- **Positions.** Expected files carry file and line positions as repository-relative paths. The
  runner rewrites the scratch prefix and nothing else. Inserting a line in a source shifts every
  position below it; that is the intended diff, and the identity-does-not-move guard proves the
  identities did not shift with it.
- **Compile cost.** The number of compilations equals the number of units. Plugin refusals need a
  unit each; post-compile refusals share one. A unit that grows past what one reader follows is
  split by the owner, not by a rule.
- **Blessed regressions.** Update rewrites whatever the tools produce. The defence is the review of
  the `expected/` diff, the identity contracts, the Scala guards, and line-oriented formats that
  keep that diff readable. No tool-side protection beyond these.
- **Partial runs.** A single case can be selected with munit's filter as today; update is refused
  under a filter.
- **Held tools.** (superseded 2026-10-18: the Go check is retired by fn-201/fn-208; no held-tool kind is needed.) A tool held for the sweep (the Go check) has no expected file kind in this spec.
  Adding one later is a new R-ID.

## Acceptance Criteria

- **R1:** A unit is discovered by its folder, and its `expected/` files alone select the tools that
  run against it, as the API contract lists. Errors: a unit with no `expected/` or an empty one
  fails naming the unit; an `expected/` file whose name the contract does not list fails naming the
  file; a unit holding two of `<root>.ir.json`, `refusals.txt` and `compile.txt` fails naming both;
  a unit without `README.md` fails naming the unit.
- **R2:** Each case compares the tool's whole output to its file after path normalisation and fails
  with a unified diff. Errors: a lift that exits 0 where `refusals.txt` is present fails with the IR
  it wrote; a package that builds where `compile.txt` is present fails; a tool whose output differs
  between two runs of one unit on one tree fails the case and the nondeterminism is fixed in the
  tool, not the runner.
- **R3:** `UMPIRE_FIXTURES_UPDATE=1` rewrites every expected file of every unit only after the
  whole run completed. Errors: a leftover or unknown expected file refuses the update naming it; a
  unit that fails R1 refuses the update; a filtered run refuses the update.
- **R4:** The Scala guards remain and pass: identity does not move with a line shift, a refused lift
  writes no IR, update writes nothing on an incomplete run, R1's refusals fire. Identity contracts
  are checked from `expected/identity.json` when present. No error surface beyond those guards'
  own assertions.
- **R5:** Every test in export and lint whose assertion reads a tool's output is replaced by a case
  and deleted; the hardcoded fixture list and the per-fixture lift tests are gone. What remains in
  export and lint test sources are the R4 guards and the runner's own tests. No error surface
  beyond R1 to R4.
- **R6:** The reify plugin's compile-time refusals have cases: each refusal the plugin can report is
  shown by a unit with a `compile.txt`. Errors: a refusal with no unit is listed in the README as
  uncovered, with its reason.
- **R7:** The framework README's testing section describes units, cases, the update flag, the
  guards, and the rule for choosing a case over a Scala test: a case when the input is a source
  tree and the output is text, a Scala test when the assertion is a Scala value or a property of the
  tool. It records the test-source line count and test count before and after R5. No error surface.

## Decision Context

The suite as measured on 2026-10-17: about 48k lines of test Scala against 41k of source, 1,162
tests in 164 files. Export carries 22k test lines for 8k of source; dsl is 15.6k against 14.9k and
is mostly native behaviour. 787 testdata files sit in some 70 folders, and 23 expected files exist.
There are 1,008 `contains(` assertions and 353 `intercept`s, and most toolchain suites set 10 or 20
minute timeouts. The expected outcome is test Scala near 20k lines with expectations in on the
order of a hundred small text files, and a new refusal case costing one source file and one update
run. The numbers are a record, not criteria.

Case folders rather than inline assertions: the one golden fixture already shows the maintenance
cost is lower and the guard is stronger (whole-file equality plus identity contracts, against
substring matches), and the Phase 3 re-anchoring rewrites every expectation regardless, so the
migration costs nothing extra if the runner exists first. Convention of files present rather than a
manifest: a manifest is a second place the contract lives and the thing the hardcoded fixture list
was. One compile per unit rather than per case: scala-cli packaging dominates the toolchain
suites' minutes, and the lifts unit shows 46 sources compile fine together. Native tests kept as
Scala rather than scripted: a script format to express `assertEquals(press(Switch, off), ...)` is a
DSL the author would read, and the owner keeps plain Scala over DSL vocabulary. Sorting line
formats in the tool rather than the runner: a sorted runner hides a nondeterministic tool.

Phasing is the owner's call. My reading of the 2026-10-17 batch order: this spec opens Phase 3's
export and lint re-anchoring, after fn-190.9/.12 land the final lifting, so the re-anchored
fixtures are written once, as cases.

2026-10-18, one-language series: owner decision "recut: ir.json internal, drop waivers". `export/` becomes `lift/` (fn-201), so the unit layout root is `lift/testdata/<unit>/`. `<root>.ir.json` stays as the lift module's internal expectation only. `<root>.waivers.json` is dropped (fn-200). `lint.txt` is the native lint's output (fn-200). The Go-check edge case and boundary are superseded. New expected kinds for Case protos (fn-203), the conformance descriptor (fn-204) and TLA+ text (fn-206) will be added as new R-IDs when those specs land, with this spec's runner discovering them the same way.
