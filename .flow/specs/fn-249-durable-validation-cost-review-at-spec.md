# Review validation cost at actual spec completion

## Conversation Evidence

> user: "every time a spec is complete, can we have a hook that asks whether we can speed up the validation gates? it's easy to accumulate validation and slow down neext specs."
> user: "we'll want the validation check to be durably recorded"

## Goal & Context

Before completing a spec in an opted-in project, the completing agent records whether its existing validation can run faster while preserving coverage. The actual spec-close command enforces the durable report so the assessment survives beyond a conversational reminder. Summarizing existing evidence should take about a minute; that is guidance, not a runtime budget gate. Include existing review overhead when known. Rough estimates and unknown costs with reasons are valid, as is “no safe savings found” with a concrete reason.

## Contract

Add the project boolean `specClose.validationReviewRequired`, off by default, and a `spec close --validation-review-file <file>` input. Only literal true enables the requirement. Malformed project config or a wrongly typed setting returns an actionable configuration error rather than silently bypassing the policy. On a genuine open-to-done transition, a supplied report is validated and recorded; opted-in projects require one. Missing required input returns an actionable question, such as “Can these validation gates be sped up without reducing coverage?”, plus instructions to assess and commit the report. The command does not wait on stdin, invoke an LLM, run validation or implement a speedup.

The small versioned JSON report names the exact spec and inventories existing gates, execution modes, measured/estimated/unknown costs, coverage, speedup decisions and reasons. Include available evidence, review overhead and Flow follow-up references where useful; unknown costs require reasons. A concrete no-safe-savings decision is valid. A spec without applicable validation records why rather than inventing a test requirement. Source-basis information is optional, and the hook validates structure rather than proving every assessment claim.

Input may be an uncommitted report under the repository, including scratch. After bounded schema/spec-ID/path validation, close copies its exact bytes into a content-addressed tracked artifact and records the artifact path and SHA-256 in the spec. Publish that artifact before lifecycle status writes and include a newly created artifact in modified_paths so the ordinary closure commit supplies durability. No extra pre-closure commit, HEAD comparison or clean-spec gate is required. A preexisting artifact must match its expected hash and bytes; otherwise refuse without overwriting it. Missing, malformed, wrong-spec, unsafe or unreadable input refuses before spec/task lifecycle writes. Existing lock/ignore-file maintenance remains separate. Close performs no evidence-tree scan, remote fetch or semantic assessment.

Already-done calls retain their existing checks/timestamp behavior, create no report obligation and preserve the prior reference even if another file is supplied. Retry revalidates explicit input and safely reuses an identical published artifact without running more work. Existing task/spec writes have no new multi-file rollback guarantee; an artifact may remain after later publication failure. Reopen retains historical metadata but requires explicit report input again for a new closure, without claiming mechanical proof of human reassessment. Task-inventory concurrency is outside this change.

Automated close forwards the conventional user-authored or staged report for an enabled project. Missing input stops before closure staging/commit or PR creation. It preserves opt-out, already-done, dry-run and body-only behavior and generates no report. Suggested follow-ups remain report content; close allocates no IDs, creates no edges and performs no optimization.

## Acceptance Criteria

- **R1:** Project opt-in, direct close and automated-close forwarding enforce a report on new open-to-done closures at the real close boundary. Opt-out projects without the flag retain current behavior. Missing input produces the actionable speedup question; invalid configuration refuses explicitly; already-done behavior and prior references remain unchanged. No extra test, LLM call, shell hook, global admission state or automatic coverage reduction is introduced.
- **R2:** The small structured report accounts for gates/modes, measured/estimated/unknown costs, coverage and speedup decisions/reasons, with available evidence and follow-ups. Exact validated input is copied to a content-addressed tracked artifact and referenced by SHA-256 in the spec, committed with the normal closure. Invalid schema/version, wrong spec, unsafe paths, unreadable input, corrupt preexisting artifacts and artifact publication failure refuse before lifecycle writes. Uncommitted input is accepted; no extra commit, HEAD-clean gate or deep evidence verification is added.
- **R3:** Isolated CLI controls establish valid closure/artifact publication, refusal before lifecycle writes, default-off compatibility, repeated-done reference preservation, retry and explicit input after reopen. Existing committed-dependency controls keep passing. These tests execute only while implementing the feature; the future close hook runs no tests or review model.
- **R4:** Repository-owned patch, project opt-in and agent/reinstall instructions deliver the feature through one cohesive implementation task. Installation stages each changed installed file from its current bytes, preserves the existing committed-dependency patch, verifies the combined result, compares per-file baseline hashes immediately before atomic replacement and retains known reversible backups. Enable this project's policy after compatible CLI and automated-close files are installed. A concurrent installation or patch mismatch stops replacement without overwriting another writer; document recovery from partial multi-file installation without claiming a cross-file atomic transaction. Other repositories stay opted out and running processes continue with their loaded code.

## Boundaries and scheduling

One cohesive M task covers patch, focused isolated tests, safe installation, project config and instructions. No functional whole-fn-247 dependency or new cross-spec edge is justified. Actual implementation and installation wait for committed fn-247.4 closure and conductor release. Narrow coordination protects the shared installed CLI, including active gomad work; global idleness or stopping unrelated sessions is unnecessary.

Preserve every existing gate, backend mode, negative control, live proof and historical receipt. The report can recommend separately tracked changes; this feature does not perform TLC batching, caching, stage deletion, coverage cuts or new CI work. Existing closed specs are not retroactively edited. Primary plan review is required before implementation. The source worker owns its focused checks and installation evidence.
