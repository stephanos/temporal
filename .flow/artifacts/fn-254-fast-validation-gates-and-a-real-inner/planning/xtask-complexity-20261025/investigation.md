# xtask complexity investigation

There is concrete accidental coupling around guest cache ownership and root resolution. The compiler/lock/admission machinery itself carries documented reproducibility requirements. Findings below come from reading the current source and callers, without running builds or tests. Design suggestions are candidates for fn-254.13/.10, not changes to their approved scope.

1. **Highest priority. Every compiled xtask command shares the guest cache identity.** `model/dev/xtask/src/guest.rs:242-250` reads the entire running executable, hashes it together with the entire workspace Cargo.lock and compiler version, copies that executable as `guest-rustc`, and selects `guest-cache/<hash>`. Line 288 sets Cargo's target directory to that cache. Thus changed executable bytes from an unrelated Apalache, retired-name, or future compiled gate/budget change select a fresh guest cache. Every guest subsequently requested with that executable uses the new namespace, including all six in `model/scripts/tests/build-guests.sh:9-16`. This does not eagerly rebuild guests that are never requested. A budget data edit that leaves executable bytes unchanged does not trigger this mechanism.

   This is an observed cache dependency, not proof of changed guest bytes. `compiler.rs:405-414` constructs the portable sidecar identity without the executable hash. `compiler.rs:267-299` propagates dependency identities and host-macro witnesses; `compiler.rs:334-358` installs portable metadata and generated-source remaps. `lock.rs:210-217` hashes per-package non-development closures. `model/GUEST_BUILDS.md:60-62` explicitly documents that an unrelated lockfile change rebuilds identical bytes. The broad key protects against stale Cargo artifacts bypassing a changed identity implementation, so simply removing its executable/lock inputs is unsafe.

   Candidate remedy is a dedicated guest-driver executable containing guest orchestration, compiler wrapping and lock admission, with the general xtask CLI invoking it. Keep hashing the exact guest driver and current lock/compiler inputs initially. Moving functions between Rust modules inside the same executable does not fix the dependency. Splitting only the rustc wrapper while still hashing the general CLI also does not fix it. Verify binary independence and current guest freshness before claiming isolated cache invalidation; no rebuild timing was measured here.

2. **Root knowledge is scattered across callers and commands.** `guest.rs:224` assumes cwd is the guest Cargo workspace and `guest.rs:79-81` reads its parent mise.toml and its local Rust toolchain file. `main.rs:24-29` instead discovers a repository ancestor containing `model/Cargo.toml`; `fetch_apalache.rs:138-142` then appends `model/build/apalache`. Shell callers supply more layout knowledge in `guest.sh:9-15`, `guest-freshness.sh:9-15`, `xtask.sh:4-15`, and `retired-names.sh:3-7`. The real Make callers are `Makefile:467,1279-1280`. `proto-go.sh:27-50` additionally owns parent `.bin` locations and literal generator/protoc versions.

   These assumptions are coherent in today's single model workspace but require coordinated edits during extraction. fn-254.13 already owns reusable root/pin/cache separation; .10 explicitly consumes it. Use one resolved context that distinguishes tool installation root, guest workspace and caller-relative outputs. Pass admitted paths into commands and keep Temporal-specific selectors in its extension. Avoid a universal ancestor search that silently discovers the parent Temporal checkout.

3. **The guest interface has duplicated remapping knowledge and a process protocol.** `guest.rs:353-357` and `compiler.rs:125-138` separately encode the same four physical-to-logical root mappings. Seven `UMPIRE_GUEST_*` values are assembled at `guest.rs:280-286` and decoded across `compiler.rs:100-103,124-141,318-329,405-406,445-454`. `main.rs:13-16` activates compiler mode only when the executable basename is `guest-rustc`; `guest.rs:249-250` must preserve that name. The protocol is documented in `model/dev/xtask/README.md:11-17`, but its invariants are distributed in the implementation.

   A private guest-context type should own environment encoding/decoding and the canonical remap list, retaining raw OS bytes. Keep argv[0] dispatch private to the dedicated guest driver or use a dedicated native compiler entrypoint. A shell wrapper would regress the documented macOS loader-variable/jobserver behavior (`model/GUEST_BUILDS.md:18-20`). The bootstrap shell already has one owner, `scripts/xtask.sh`; its existence is justified by the need to build a host tool before guest wrappers and flags are installed. Avoid replacing it with another framework of launch adapters.

Preserve compiler input normalization, host-macro witnesses, lock/source ambiguity refusal, pinned archive/JAR admission, sidecar leases, and atomic publication. Their removal would weaken the contract, even if it shortened the files. The smallest clean shape is a thin general command dispatcher, one deep guest-build module behind a dedicated executable, a resolved tool/workspace context shared by command implementations, and the existing installer/scan implementations. Additional crates or generic process-runner abstractions need demonstrated callers. The exact best package split remains a design choice; this investigation establishes the dependencies, not a proven relocation implementation.
