## Scope contradictions and unresolved contract choices

These findings distinguish captured owner-backed outcomes from details tagged inferred in the spec. They should be resolved in the plan rather than buried in implementation.

- **Capacity error versus backpressure.** R1 requires blocking when the write buffer is full; inferred R11 says exceeding a byte limit returns resource-exhausted. Current simulation code blocks at its per-connection chunk limit but fails at global delivery/byte limits (`simulation_handles.go:162-175`, `:197-205`). The plan must name which byte limit blocks, which is a hard resource failure, and the partial-write/error precedence. Applying either rule to all limits contradicts one captured criterion.
- **Bytes-only scope.** Architecture line 67 specifically removes chunk-count limits. R11's broader wording could also remove listener, connection and transition count bounds. Existing `Limits` has all five network fields (`spec.go:77-81`), and record validation enforces those bounds (`record.go:811`, `:840`). The network rewrite needs bounded metadata and history even for zero-byte connections. Treat removal of chunk/delivery counts separately from retention of object/history bounds; make the interpretation explicit.
- **Default versus zero.** Inferred R6 requires a documented default and rejects zero. Current `DefaultLimits()` explicitly returns populated values (`spec.go:130`), while `validateLimits` rejects zero and above-maximum values (`:314-347`). An explicit default constructor/helper is consistent with that contract; silent normalization of explicit zero is not. No source evidence chooses a stall duration. The parked unknown remains open until a value is justified against workload deadlines. Configuration needs positive finite nanoseconds and safe deadline arithmetic, with propagation through generated network config, both backends and recorded simulation identity.
- **Timeout versus caller deadline.** R4 resets both endpoints permanently with timeout classification; R1/R2 preserve usability after an operation deadline. Current reset reads/writes yield ErrClosed (`simulation_handles.go:85-88`, `:157-160`), and the process codec collapses recognized deadline errors to os.ErrDeadlineExceeded. Preserve these two outcomes distinctly. Inferred R5 extends stall timing to a pending dial, which has no established connection buffer. Specify its timer start/reset and heal/deadline/stall tie policy explicitly; current dial waits on topology/context only (`simulation_network.go:398-445`).
- **Directed partitions.** R2 says no data crosses in either direction, while the edge section explicitly preserves asymmetric directional links. Reconcile R2 as no crossing of each disabled directional link, and prove the enabled reverse link remains usable until a connection-wide timeout reset. That interpretation follows the established directional model, but remains a planning recommendation.
- **Replay simplification versus divergence fidelity.** R10 removes per-delivery steps and payload hashes, but existing same-length payload corruption is detected before write mutation. If the replacement history carries only write length and outcome, network replay alone loses that distinction. Define the retained observation that detects changed payloads, its bound, and when it rejects. Existing deterministic-I/O recording supplies read/write byte observations (`simulation_handles.go:99`, `:207`); whether that covers every direct simulation and replay entry point needs proof. Do not describe “still detects divergence” as satisfied by matching lengths alone or by removing the negative control.
- **No second connection type.** R9 should unify the two stateful queue engines; it must allow process RPC and descriptor adapters, which have distinct transport/nonblocking duties. Fn-109.17's backend-specific factories remain compatible with that goal. The fn-154 architecture's hook proposal is source-tagged inference, not a requirement to retain a particular callback design.
- **Continuous stalled time and retained delay.** R4 and the edge section require timers only while undelivered data remains and continuous stalled time resets after heal. They do not settle same-instant heal/timeout ordering, already-readable versus in-flight bytes, or whether a second partition during post-heal delay restarts the same delay. Specify these observable cases and tie ordering before splitting tasks, while preserving R2/R3's complete ordered stream.
