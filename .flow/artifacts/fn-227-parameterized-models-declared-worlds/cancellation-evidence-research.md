# fn-227.5 cancellation evidence research

The existing observations cannot supply `asynchronous_cancel` as a Start option. ## Primary-source findings

Paths below are repository-relative unless prefixed `/home/agent`. Define API as `/home/agent/go/pkg/mod/go.temporal.io/api@v1.63.6-0.20260909222256-20151aa90480` and SDK as `/home/agent/go/pkg/mod/go.temporal.io/sdk@v1.48.0`. These are the versions pinned by `go.mod:77,79`; `model/temporal/hosts/go/go.mod:7` pins the same API. This report concerns those versions and the local server revision, without claims about later releases.

1. Start contains the four timeouts and retry policy, but no cancellation-mode field. Its completion callbacks run on terminal state. The response identifies the run and whether a new activity started, but supplies no cancellation mode either. Cancel carries namespace, activity/run IDs, identity, request ID, and reason. Sources: `API/workflowservice/v1/request_response.pb.go:16570-16640`, `:16826-16836`, `:18393-18408`. In particular, a successful Start with `started=false` may refer to an existing run; new request options cannot establish that existing run's World (`:16828-16831`).

2. Standalone SDK Start options likewise have no cancellation mode, and its private completion callbacks are terminal notifications. Standalone Cancel options contain only Reason; Cancel returns the cancel RPC error immediately, with no wait-for-terminal operation. Sources: `SDK/internal/internal_activity_client.go:31-122`, `:228-231`, `:812-828`. Workflow activity `WaitForCancellation` is a separate caller policy: the SDK issues the cancellation command and resolves its local callback immediately when the wait flag is false. Sources: `SDK/internal/activity.go:140-144`; `SDK/internal/internal_event_handlers.go:838-846`. Mapping that workflow-only flag onto standalone server state would conflate two contracts.

3. The public RPC contract explicitly documents cooperative cancellation, acknowledgment, and delivery through heartbeat `cancel_requested`. Source: `API/workflowservice/v1/service_grpc.pb.go:799-805`. The server applies CancelRequested and immediately closes only when no attempt is in progress. With an attempt, it returns the response while cancellation remains pending. Source: `chasm/lib/activity/operator_commands.go:258-285`. This is an inherent protocol/state property, not a Start option or a choice made by the caller's wait policy.

4. Describe can show actual pending cancellation through status RUNNING plus run_state CANCEL_REQUESTED. Sources: `chasm/lib/activity/responses.go:21-28`, `:48-64`, `:81-86`. That is evidence of the current run's state after cancellation, not a pre-start parameter or proof of all future behavior. The current realization refuses this combination. Source: `model/temporal/feature/activity/phase.rs:19-28`.

5. A heartbeat sets `CancelRequested=true` in its response and leaves the server in its current state. Actual cancellation acknowledgment uses `HandleCanceled` and TransitionCanceled. Completion is permitted from CANCEL_REQUESTED and transitions to COMPLETED; failure is permitted from CANCEL_REQUESTED and transitions to FAILED. Sources: `chasm/lib/activity/activity.go:592-624`, `:525-547`, `:451-471`; `chasm/lib/activity/statemachine.go:128-157`, `:192-200`. Consequently, binding `asynchronous_cancel=true` alone does not make the spec's “next worker response or heartbeat closes as Canceled” rule conform. This is a contract discrepancy to expose, not permission to revise the independent Model.

6. Existing live control `Cancellation` cancels the runner context and checks that the SDK body exits with context.Canceled. It does not issue the server cancel RPC. `CancelBeforeWorkerStart` does issue that RPC and verifies terminal Canceled without a worker. Sources: `tests/testpilot_model_slice_test.go:292-296`, `:226-242`, `:251-266`. Complete, Fail, and HostRefusal exercise independent callback behaviors (`:298-329`); retain them. The current callback implementation supports Complete and nonretryable Fail only (`model/temporal/feature/activity/temporal.rs:169-195`), and its cancel projection consumes only the RPC result (`:40-55`). None supplies a selectable cancellation mode.

7. Observation currently contains only method and result, with no request. Source: `model/temporal/proto/umpire/temporal/v1/temporal.proto:10-16`. Runtime owns its machine, current state, freeze state, and exploration; the realization methods cannot replace the machine. Prepared transactions currently change exploration or run state, and native dispatch commits only after successful response encoding. Sources: `model/umpire/wasm/src/runtime.rs:66-105`, `:118-139`, `:376-394`. Thus actual Start request/result binding and World replacement still require an explicit admission seam; this report finds no existing hidden source of that evidence.

## Recommendation requiring an owner contract

The smallest provenance amendment is to replace “cancellation type from Start options” with this explicit contract:

> Retry and timeout parameters come from the actual filled Start request paired with its successful new-run response. Cancellation semantics come from an explicitly declared, versioned standalone-activity protocol binding, supported by the public cooperative-cancellation contract and independently checked using actual cancel, heartbeat, acknowledgment and Describe observations. They are never inferred from nonexistent request fields, callback payload labels, or an SDK caller wait setting. Missing or unsupported binding evidence refuses admission with `asynchronous_cancel` named.

This is a proposal, not an approved requirement change. It preserves the World field and actual evidence boundary while distinguishing request-derived parameters from protocol semantics. It needs one additional owner determination before implementation: does the independently intended Model require cancellation to win over every completion/failure and heartbeat, or does it intend the public cooperative contract? If the stronger promise is intended, preserve it and report the implementation disagreement. If cooperative behavior is intended, authorize the Model contract correction independently before changing transitions. Merely selecting true silently would hide this second issue.

After that decision, bind the chosen protocol contract and the actual Start request/result in the same admission transaction as World/state replacement and exploration invalidation. Reject unsuccessful Start and handle existing-run responses explicitly. Publish no new World if response encoding/allocation fails. Keep malformed ordinary observations state-preserving; implement R6's field-naming Unsupported-plus-freeze specifically for out-of-domain admission. This extends the existing transactional mechanism cited in finding 7 rather than constructing state from intended SDK options.

Preserve all current controls and add a distinct server-cancellation control with a held started attempt, actual successful cancel, Describe RUNNING/CANCEL_REQUESTED, heartbeat notification, actual cancellation acknowledgment, and terminal Describe. Also retain a completion-after-cancel control so the chosen promise cannot be made true by suppressing contradictory observations. These are recommended future checks, not executed evidence. Existing sources establish the missing admission input and contract discrepancy; no existing observation can retroactively provide the requested Start cancellation type.
