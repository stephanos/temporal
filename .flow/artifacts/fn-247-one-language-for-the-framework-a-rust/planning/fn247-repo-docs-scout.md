## Process mechanism and unsafe ownership

The current ownership mechanism is stronger than process-group termination. `process.py:35-38,57-72` sets a Linux subreaper, kills adopted descendants, and reaps descendants that created a new group. `process.py:16-20` refuses root/effective-root on Darwin and applies RLIMIT_NPROC zero in the target child. Owner stdin EOF, TERM/INT/HUP/QUIT, separate target sessions and exact signal exit mappings are part of the source contract at `process.py:27-75`.

A separate executable needs a proven build/discovery contract for `cargo test -p umpire-tlc`, `cargo test -p umpire-apalache`, a process library unit test, renamed external path consumers and custom CARGO_TARGET_DIR. Depending on a sibling binary produced by workspace --all-targets or Make ordering fails those cases. Cargo's per-package CARGO_BIN_EXE support does not automatically deploy a dependency's binary beside arbitrary downstream consumers. This repository contains no reusable supervisor packaging solution. Nested Cargo builds, unstable artifact dependencies and a runtime Cargo invocation would add build/tool contracts that the plan must establish first.

For a concrete decomposition without that deployment problem, choose an allocation-free libc-only supervisor path after fork. The owner prepares command arguments, environment, executable resolution, descriptors and buffer storage before forking. The child supervisor uses audited libc process/descriptor operations and stack-only scalar/byte-slice loops until `_exit`; the target branch applies setsid and platform restrictions before exec. Linux adopted-child enumeration needs bounded stack parsing with repeated reads that preserve the existing unbounded descendant cleanup responsibility. Fixed buffers must not silently drop PIDs or reduce ownership.

The invariant must prohibit allocation, formatting, Rust locks, panics, error unwinding and destructor work in every post-fork branch. Error reporting needs a fixed binary pipe protocol decoded by the allocating owner. Signal handlers record only the first signal through lock-free signal-safe storage. Explicit descriptor closure must keep the owner's liveness writer out of target descendants. A raw fork followed by the current allocating Rust loop would violate this design. The implementation must audit the exact platform libc operations and include a concurrent parent-thread allocator control as well as the existing owner-death/escaped-grandchild controls. This recommendation is source-derived design, not an executed feasibility result.

`model/Cargo.toml:104` sets unsafe_code to forbid. A module-level allow cannot override an inherited forbid. The existing ABI precedent is `protocol/runtime/Cargo.toml:26-48`, which repeats the workspace lint values locally with unsafe_code deny, and `protocol/runtime/src/abi.rs:139,146,153`, which allows only three export attributes. Apply that existing mechanism to the new process crate. Leave workspace forbid unchanged, repeat its lint values with crate-local deny, and allow unsafe only in the process-owned syscall module. The rest of that crate remains deny and all other crates retain their present policies. Avoid specifying both workspace lint inheritance and local overrides. libc constants used by safe APIs do not require unsafe exceptions in xtask.

Preserve the Rust owner's regular-file capture and retained-handle checks in `process.rs:206-230,251-280`; merging stderr temporally or switching to unread pipes changes output/deadlock behavior. Preserve stdout-before-stderr concatenation, bounded invalid-UTF8 output, dump depth/entry/byte checks, cancellation distinction, private 0700 scratch directories, final safety checks and reported cleanup failure. Current heap_mb is a Java setting, not an OS memory ceiling. Polling budgets can be exceeded temporarily between 5ms checks. The plan must not claim stronger resource enforcement than the source provides.
