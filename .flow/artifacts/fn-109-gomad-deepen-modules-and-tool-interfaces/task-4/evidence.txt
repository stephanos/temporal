Design
- New cmd/gomad/internal/cli/application.go. Run builds one private `application` per invocation
  (hostApplication: os.Executable, os.Getenv, os.Stdin/os.Stdout, runner.DispatchPrivateMode) and
  dispatches through app.run. The application alone:
  - names the private child modes (__coordinator, __supervisor, __target_bootstrap) and dispatches
    them over the process streams (app.runPrivateMode);
  - finds the executable (executablePath, absoluteExecutable), resolves the installation from
    --toolchain-root / GOMAD3_TOOLCHAIN_DIR / adjacent manifest (resolveInstallation) and digests the
    Runner build (digestRunner);
  - returns an `installation{toolchainRoot, executable, runnerBuild}` whose supervisorCommand() /
    coordinatorCommand() are the only place child-mode argv is spelled.
- Commands that need an installation are application methods (explore, plan, execute-shard,
  qualify, qualify-set, analyze, resume, replay, minimize, doctor). They feed app.install (or
  app.executablePath / app.installedToolchain / app.resolveInstallation) into their existing
  dependency structs. The former `identity func(string) (string, string, string, error)` seam is
  now `install func(string) (installation, error)`; analyze keeps its `toolchain` seam and
  qualify-set its `executable` seam. No package-global hook was added (no new `var`).
- Resolution stays lazy: each command asks for its installation at exactly the point it used to
  call localIdentity / os.Executable, so input validation still precedes installation errors, plan
  still resolves the installation before requiring --output, and doctor still names its executable
  before parsing flags (pinned by TestApplicationResolvesOnlyAfterInputValidation).
- Explore, plan, replay and execute-shard gained dependency structs in the characterization commit
  (exploreDependencies, replayDependencies, campaignShardDependencies) so their requests and outputs
  are observable without a toolchain; behavior unchanged (captures below are identical).
- Runner build digest: the doctor check's streaming digest (open, regular+executable check, SHA-256)
  is now the single owner, used by both doctor's Check and install. Previously install read the
  whole executable with os.ReadFile. The digest bytes are identical ("sha256:%x"). Two failure
  behaviors change. (1) When the running executable cannot be opened, the text changes from
  "hash gomad executable: open ..." to "hash gomad executable: open Runner: ...". (2) The
  regular-executable check is new for install: a running executable that stops being a regular
  executable file after startup (for example `chmod -x` on the binary while gomad starts) used to
  be hashed and accepted, and now fails with "hash gomad executable: Runner is not a regular
  executable: PATH". Both exit 3 with classification runner_failure. Pinned by
  TestApplicationInstallFailsClosed. (Reworded after the fn-109.4 review: an earlier version of
  this note called the case unreachable.)
