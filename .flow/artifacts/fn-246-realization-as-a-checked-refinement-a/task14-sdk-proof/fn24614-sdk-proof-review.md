## Finding

**P2. Synchronize the late-switch control with the SDK batch flush.** At `model/temporal/hosts/go/reference/worker/sdk/heartbeat_test.go:389-395`, the test assumes that the first 100 ms throttle window remains open until the second command reaches `activity.RecordHeartbeat`. The first actual true completion and SDK cancellation do not establish that assumption. If the test goroutine or process pauses after the first call long enough for the empty timer window to expire, the SDK clears `hbBatchEndTimer`. The second call then uses its detached context to start a fresh RPC successfully. The mock receives an unexpected second request and the test waits for a completion until its 10 second Run timeout. This can fail under scheduler delay while the SDK behaves correctly.

The pinned SDK mechanism is explicit in `/home/agent/go/pkg/mod/go.temporal.io/sdk@v1.48.0/internal/internal_task_handlers.go:2186-2189,2201-2228`. A buffered call replaces only `lastDetailsToReport`. The timer goroutine retains the context of the call that opened its window. When the timer fires, it clears `hbBatchEndTimer` even if there are no pending details, then re-enters `Heartbeat` with that retained context only if details were pending.

A public SDK control can avoid depending on the 100 ms deadline. Use a long throttle, complete the first original-context call with actual true, await actual SDK cancellation, and submit the second detached call while it is buffered. Start public `worker.Stop` asynchronously while keeping the Run alive. `activityWorker.Stop` closes its `stopC` before waiting for task processing (`internal/internal_worker.go:672-675`). The existing heartbeat timer selects that same worker stop channel (`internal/internal_task_handlers.go:2207`) and flushes pending details through the original opening context. The control can then observe the canceled transport invocation, return the handler's terminal choice, and join the Stop call through a once-owned, waitable wrapper. A first-window detached positive control under the same shutdown trigger would distinguish the two opening contexts. The existing fixture's `f.stop` cannot serve as that trigger because it cancels the Run before calling `worker.Stop` (`heartbeat_test.go:269-274`).

Returning a failed terminal to force a flush would test a different mechanism. SDK `invoker.Close` uses the original activity context captured before execution (`internal/internal_task_handlers.go:2418-2423`) and calls `internalHeartBeat` with that context (`2312-2320`). After true, that close flush can fail even if the timer window originally used a detached context. It would not isolate the late-switch timer hazard.
