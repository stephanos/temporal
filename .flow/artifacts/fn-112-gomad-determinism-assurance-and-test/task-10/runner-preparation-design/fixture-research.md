## Why two private dependencies are necessary

`CampaignSpec.Preparer` is only the inner target preparer. `internal/preparation.prepareWith` calls it, overwrites its adapter projection with the owner's selected adapters, and still validates the complete prepared target (`tools/gomad3/internal/preparation/preparation.go:69`, `:97`, `:101`). A custom preparer skips adapter discovery but never bypasses the validation at line 102. `deterministicio.Spec.ValidatePreparedTarget` invokes the public host guard first (`tools/gomad3/deterministicio/profile.go:278`, `:293`). That explains why these fake target/executor combinations still stop on linux/arm64.

After preparation succeeds, `runSeed` creates its real partial directory and output files, then calls `profile.BootstrapFrame` before the executor (`tools/gomad3/runner/runner.go:651`, `:668`, `:685`, `:716`). `BootstrapFrame` independently calls the same public host guard (`tools/gomad3/deterministicio/bootstrap.go:25`). A preparation-only seam therefore moves the failure later without reaching the intended assertions.

Use private, explicit per-invocation functions on the existing `executionDependencies`, which currently contains only `executor` (`tools/gomad3/runner/runner.go:123`). The seam research proposes these shapes:

```go
prepare func(context.Context, preparation.Request) (target.Prepared, error)
bootstrapFrame func(deterministicio.Spec, target.Prepared, string, uint64) ([]byte, error)
```

The production defaults remain lazy calls to `preparation.Prepare` and `profile.BootstrapFrame` at their existing sites. Carry the optional dependencies through `campaignRequestFromSpecWith` and the private runtime owner, which currently forwards only the executor (`tools/gomad3/runner/campaign_options.go:90`, `:210`). This is a private function seam, with no new exported test API or mutable package hook. The separate seam report owns the final production propagation design.

The real local owner continues to begin/complete preparation and record its plan (`tools/gomad3/runner/runner_local.go:243`, `:293`). It retains controller accounting, output-file lifecycle, target verification, World assessment, journal transactions and publication. In particular, target verification precedes World decoding at `runner_local.go:527` and `:566`; a fixture must never replace either operation.
