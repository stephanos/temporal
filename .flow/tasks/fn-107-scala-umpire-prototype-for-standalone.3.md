### Approach
- **Tables.** Rebuild the check view with `umpire.NewTable` from each goir `Machine`:
  - same keys and rows;
  - `Result.Step` set from `Transitions[i].Steps[j]`;
  - `TableSpec.Assumptions` from IR `assumes`, with `fair` action ids mapped to `Action.name`;
  - `TableSpec.RefinedField` for refining machines;
  - `TableSpec.Unknown` from `mm.Holes`.

  Empty step lists stay disabled (absent pairs). Never convert a hole to disabled or a disabled pair to a hole.
- **Claims.**
  - Bind IR Property, Scenario and Query (find, verify, `through`) through task 17's key-level constructors. `through` uses `RefineTables` with the IR map and visible projection.
  - Scope claim bindings and receipts by (family, machine-or-composition, local name). `PropertyID`/`ScenarioID` and their Go/Lean pins stay unchanged. S5 is recorded, not fixed.
  - Kind-check every claim-function result (holds, monitor next/violated/after, progress from/to). A non-Bool or out-of-domain result is a located definition error.
  - Pass the classifier `errors.As(err, *goir.Hole)`, so a hole inside a claim function is unknown evidence (S6), never `false`.
- **Monitors.** Bind machine monitors through `KeyMonitor`. Monitor history stays in product identity, and a monitor never suppresses a behavior. A Query over a composition whose member declares monitors returns a located **`unsupported`** receipt (S2 undefined). Machine-monitor semantics and task-2 feature sources are untouched.
- **Compositions.**
  - Bind IR compositions through `ComposeTables`: members by field, syncs and `ends`, with an explicit ceiling.
  - Build the composed step record as model/go and Scala read it: the state record from member values, with String `<field>_<key>` outcome and facts. Record this in SEMANTICS (S3).
  - Replacement uses `RefineTables(…, CoverStarts:true)`.
  - Composition starts are the Cartesian product of every member `Table.Starts`. Scala's `starts.head` divergence is noted as future front-end work and not reproduced.
- **Refinement.** Check initial correspondence plus visible event/result projection, reject public-output stutter, and enumerate opaque-provider behaviors under selected bounds. Receipts carry `RefinementError.Kind`, `Witness` and `ProductWitness`, and assert agreement with `mm.Refinement`/`mm.Rejected`.
- **Progress.** Bind deadline, deadlock and fair-cycle claims through `KeyProgressFunc`/`CheckProgress` with explicit assumptions. Report unestablished progress as unresolved rather than infer it from a prefix. Read `ProgressAnswer.Unknown` for holes.
- **Guard.** Test-first Kind guard for `ends`/`visible`/`visible_outcomes` (`end_visible_fix.md`).
- **Receipts.** Keep these kinds distinct: admission-error, declaration-error, resource-limit, limit-reached, unresolved, refinement-rejected, counterexample, verified-within-limits (complete), incomplete(hole: name + row, or claim edge), unsupported, replay-failed.
  - A counterexample or found witness is never downgraded by an unrelated hole.
  - An explored hole makes an otherwise-verified or not-found result incomplete.
  - An unexplored or out-of-bound hole taints nothing.
  - An `unsupported` receipt is never reported as a check, a proof or verified coverage.
- **Replay.** Replay every generated witness (`Table.Replay`, `Query.Replay`, `Progress.Replay`) against a table from a fresh `Build` before finalizing a receipt.
- **Tenfold probe.** Add a tenfold finite-input probe with explicit small ceilings at check level (Query `Search`, `CheckProgress` `Search`, `ComposeTables` ceiling). Under sufficient ceilings, assert complete coverage. Under insufficient ceilings, assert an explicit resource-limit result, keeping the actual scope and work counts and never claiming that truncated exploration is exhaustive.

### Decisions that differ from the task text

Twelve decisions. The review accepted all but decision 4.

1. **Thirteen receipt kinds, not eleven.** The listed kinds have no name for a `find` that finds or that finds nothing, so `found` and `not-found` join them.
2. **A `through` Query over a rejected refinement is `refinement-rejected`.** `RefineTables` returns no `Refinement` to read through, as typed `VerifyRefined` returns the refinement error. `staleAdmission.product.pausedIsNotDispatched` therefore reports the rejection with its witness, and the stale design's violation shows in its own five counterexamples.
3. **A `through` Query over a refinement left incomplete by a reachable hole runs over a hole-free twin table.** A counterexample stands with the holes listed. Any other answer is `incomplete`, naming the refinement's reachable holes. This marks `putStoresThroughDisk` incomplete although its pinned Scenario never schedules the crash, because the refinement it reads through is itself unestablished.
4. **Withdrawn in review round 1.** The first version made the whole Model one `incomplete` receipt when a hole was reached outside any step. A failure to interpret a machine, or to evaluate its refinement, now stays with that machine and what depends on it.
5. **Two more `unsupported` cases.** A `find` with `through` has no key-level constructor, and a transition Property with a `when` has no meaning in SEMANTICS or in `KeyTransitionProperty`.
6. **A composition that builds and replaces nothing has no receipt.** Building it checks nothing. A composition with a replacing member gets one receipt for the replacement, and any composition that fails to build gets one, which its Queries inherit.
7. **Replacement is checked twice.** The binding runs `RefineTables` with cover-starts itself before `ComposeTables` repeats it, so a failure names the member machine whose holes and tables the receipt reads.
8. **A claim-function error names the step's target state, not its row** ("for the step into staged"). A key-level Property callback receives the `Result` and no row key.
9. **A refinement map that returns a value outside the refined machine's states is a `declaration-error`.** `Build` reads the same Model as a rejected refinement, and the agreement check is skipped for that case.
10. **`Result.Step` is set as the task says, and a through-read still rebuilds the record from keys,** because `keyStep` returns a `Result` with no `Step`. The two paths give equal records.
11. **`Scope` adds `QuerySearch` and `Progress` limits.** The IR gives a progress claim only `within`, and the probe needs to lower a Query's declared search limit without editing the Model.
12. **One fresh `Build` per `Check` serves every replay,** made when the first witness needs it.

### The structural pass: one helper for every fold

`fold(parts ...Receipt) Receipt` in `checking.go` is now the only place one result is weighed against another. Its rule:

- **Precedence**, highest first, and the first of several of one level: `replay-failed`, `admission-error`, `declaration-error`; then `refinement-rejected`, `counterexample`; then `resource-limit`, `limit-reached`, `unresolved`; then `incomplete`; then `unsupported`; then `verified-within-limits`, `found`, `not-found`.
- The receipt is the winning result, whole.
- It lists **every hole of every input**, in input order, each once.
- The new field `Receipt.Also` holds **every other input whose witness the receipt does not carry**.
- A `verified-within-limits` or `not-found` beside any hole is `incomplete`, and an `incomplete` receipt's explanation is written from all of its holes.

`TestFoldKeepsTheKindOfHighestPrecedenceAndEveryHoleAndWitness` checks the helper directly over all 169 ordered pairs of the 13 kinds against a precedence table written out in the test, with whole-receipt equality, plus a single input, a shared witness and three inputs.
